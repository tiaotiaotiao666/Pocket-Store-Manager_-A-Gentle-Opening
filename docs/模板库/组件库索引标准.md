# 组件库索引标准

> 更新日期：2026-11-09。
> 适用对象：需要从当前唯一 Base 模板组合新页面、复用区块，或把视图包区块提升为正式组件的 Agent。
> 机器契约：`templates/registry/schema/component-catalog.v1.json`；实现：`scripts/component-catalog.cjs`；生成物：`templates/catalog/`。
> 本文是“Agent 怎么读组件库”的唯一入口。源码、Manifest 与 Base 页面仍是事实源；catalog 是它们的确定性投影，不是第二份源码。

## 1. 解决什么问题

当前唯一模板 `ordering-base@1.0.0` 已经在 `templates/base/ordering-base/1.0.0/src` 中实现 14 个微信原生组件、8 个页面，另有 1 个 Feature Pack 组件和 1 个 FrontendPack 视图包。这些文件对 Composer 是可执行的，但对 Agent 不是“可检索的能力库”：

- 组件能力分散在 `index.js` 的 `properties/methods`、`index.wxml` 的绑定、`index.wxss` 的主题变量和页面 `usingComponents` 中；
- 同名 UI Block 只有 3 个完成 Manifest 登记，其余 Base 内置组件没有统一卡片；
- 页面区块只有 WXML 结构，没有“哪些区块可复制、哪些必须走插槽、哪些应提升为组件”的判断；
- Agent 直接读源码容易把 Base 固定组件误当成可通过 `Plan.components` 注入的资产。

组件库目录把这些事实投影成四层可读对象：

```text
组件（components）  → 我能用什么、怎么传参、会发什么事件、不能做什么
页面（pages）        → 这个页面由哪些组件与插槽组成、控制器有哪些方法
布局（layouts）      → 视图包覆盖了哪些页面、区块顺序与插槽锚点
区块（sections）     → 页面里的某一块能否复用、怎么复用、是否该提升为 UI Block
```

## 2. 目录结构

```text
templates/catalog/
├─ index.json                         # 唯一检索入口
├─ curation.v1.json                   # 人工知识层（用途、场景、约束、区块定义）
├─ components/<id>.json               # 15 个组件卡
├─ pages/<pageId>.json                # 8 个页面装配卡
├─ layouts/<packId>@<version>.json    # FrontendPack 布局卡
└─ sections/<packId>@<version>/<pageId>/
   ├─ index.json                      # 页面区块索引
   └─ <sectionId>.json                # 23 个区块卡
```

禁止手改 `index.json`、`components/`、`pages/`、`layouts/`、`sections/`。人工知识只写在 `curation.v1.json`，然后执行：

```powershell
npm run catalog:write
npm run catalog:check
```

## 3. Agent 阅读协议

### 3.1 先读索引

`templates/catalog/index.json` 的 `readOrder` 是固定顺序。实际检索时按以下字段筛选：

| 我要做什么 | 读什么 |
| --- | --- |
| 找一个能展示/交互的组件 | `components[]` 的 `category`、`props`、`events`、`pages`、`slots` |
| 确认组件怎么传参 | `components/<id>.json#interface.props` |
| 确认会发什么事件 | `components/<id>.json#interface.events`，`payload` 是 detail 字段名 |
| 确认组件能不能被 Plan 注入 | `components/<id>.json#runtime.mode` 与 `planConsumed` |
| 复刻一个页面的结构 | `pages/<pageId>.json#components`、`slots`、`controller` |
| 换一套首页/菜单布局 | `layouts/<packId>@<version>.json#pages[].blocks` |
| 只复用页面中的一块 | `sections/<packId>@<version>/<pageId>/index.json` |
| 判断某块能否提升为组件 | 区块卡的 `reuse.level` 与 `uiBlockBlueprint` |

### 3.2 再读单卡

单卡字段按“身份 → 契约 → 用法 → 约束 → 验证”排列。Agent 至少读完以下字段再写 Plan：

1. `sourceKind`：`base-builtin`、`registry-ui-block`、`feature-pack`。
2. `runtime.mode`：决定它是否会被 Composer 消费。
3. `interface.props/events`：名称、类型、默认值、必填、payload。
4. `dataModel.fields`：对象型 prop 的字段约束。
5. `constraints` 与 `knownLimits`：不能做什么、已知边界。
6. `source.files`：需要读原始实现时的准确路径。
7. `verify.command` 与 `digest`：卡片是否与源码同步。

### 3.3 最后读源码

只有以下情况才需要打开 `source.files`：

- 要确认 WXML 的类名、层级或条件渲染细节；
- 要确认 `observers` 的派生逻辑；
- 要判断一个区块能否复制，需要看样式作用域；
- 卡片与源码出现 `content drift` 时，先执行 `npm run catalog:write`，不要直接改卡片。

## 4. 字段契约

完整字段以 `templates/registry/schema/component-catalog.v1.json` 为准。这里只解释 Agent 最容易误读的字段。

### 4.1 组件卡 `runtime`

| `mode` | 含义 | Agent 应做什么 |
| --- | --- | --- |
| `base-page-fixed` | 组件随 Base 页面固定导出，`Plan.components` 当前不会复制或替换同名组件 | 只能通过 FrontendPack 改页面结构，或通过插槽 Feature Pack 替换区块 |
| `registry-validation` | 已登记 UI Block，通过 Manifest、预览与边界校验，但当前不从 `Plan.components` 复制 | 把它当契约与预览资产；运行时仍使用 Base 同名组件 |
| `slot-injection` | Feature Pack 组件，通过 `features[].slots[]` 注入 | 在 Plan 中写精确版本与插槽 props；换位只写顶层 `slotOrder` |

> 当前 Composer 的已知偏差：`Plan.components` 不覆盖 Base 同名组件。不要因为卡片存在就假设“写了 Plan 就会替换页面里的组件”。

### 4.2 组件卡 `interface`

- `props[].name` 是 camelCase；WXML 属性必须转 kebab-case（例如 `totalCents` → `total-cents`）。
- `props[].defaultValue` 是源码默认值，不是页面必传值；`required=true` 才是业务必填。
- `events[].payload` 是 `triggerEvent(name, detail)` 的 detail 顶层字段；detail 不应出现未声明字段。
- 金额字段只允许整数分；卡片的 `dataModel.moneyRule` 是统一说明。

### 4.3 页面卡

- `components[].mode`：`always`、`conditional`、`modal`、`declared-only`。
- `declared-only` 表示页面 `usingComponents` 声明了该组件但 WXML 未使用；Composer 导出时会过滤。不要把它当作当前页可用组件。
- `controller.methods` 是页面业务方法；`controller.lifecycle` 是 `onLoad/onShow/onPullDownRefresh` 等生命周期。FrontendPack 的事件绑定只能命中这两类中真实存在的方法。
- `slots[].dataKey` 是导出配置键；`menu-hero` 的映射固定为 `menuHero`，即使 `slots.json` 镜像尚未登记。

### 4.4 布局卡

- `blocks[].depth` 与 `parentClass` 表达区块层级；`sourceLine` 可直接跳到 WXML。
- `blocks[].components` 是直接归属该区块的组件；嵌套区块的组件归属最内层区块。
- `blocks[].slots` 是包含在该区块范围内的插槽；插槽锚点必须完整保留。
- 布局卡只描述视图包，不包含任何 JS；控制器来源固定写 `Base pages/<pageId>/index.js`。

### 4.5 区块卡

| `reuse.level` | 含义 | 复用方式 |
| --- | --- | --- |
| `direct-wxml` | 纯展示、无数据契约负担 | 复制 `template.snippets[].code` 与 `styles.selectors` |
| `base-component-use` | 本质是对 Base 组件的调用位 | 直接调用对应组件，不复制组件实现 |
| `slot-only` | 插槽容器或 fallback | 通过 Plan 的 `features[].slots[]` 或 `slotOrder` 使用，不复制 WXML |
| `promote-to-ui-block` | 视图包自有视觉，其他模板要复用应先提升为 UI Block | 按 `reuse.uiBlockBlueprint` 新建资产、登记、冻结，再进入页面 |

区块卡的 `controller.verified=true` 是硬门禁：区块绑定的每个 `bind:/catch:` 处理函数都必须能在 Base 页面控制器中找到。

## 5. 与注册表和 Composer 的关系

```text
Base 源码 / Manifest ─┐
Registry 索引 ─────────┼─→ component-catalog.cjs ─→ templates/catalog/
FrontendPack 视图 ─────┘
```

- catalog 不登记进 `registry.v1.json`，不参与 Composer 的资产解析、Plan 校验或 Lock 摘要。
- catalog 的 `digest` 只用于发现“卡片过时”。源码改动后必须重新执行 `catalog:write`；它不会改 `registry.lock.json`。
- 资产内容改动（Base、UI Block、Feature Pack、FrontendPack）仍然必须先执行 `node scripts/registry-check.cjs --write` 重新冻结，再生成 catalog。
- 把区块提升为 UI Block 时，必须按 [`组件入库标准.md`](组件入库标准.md) 新建 `templates/components/` 资产并登记；不能只改 curation。

## 6. 门禁命令

```powershell
# 资产改动后先重冻结
node scripts/registry-check.cjs --write
npm run registry:check

# 重新生成组件库目录
npm run catalog:write

# 校验目录与源码同源（CI / 提交前必须 exit 0）
npm run catalog:check

# 目录卡单元测试
node --test test/component-catalog.test.cjs

# 全量回归
npm test
```

`catalog:check` 会做：

1. 重新扫描 Base 组件、Registry UI Block、Feature Pack 与 FrontendPack；
2. 重算组件卡、页面卡、布局卡、区块卡与索引；
3. 与磁盘逐字节比较，发现缺文件、多文件或内容漂移即失败；
4. 校验组件 props/events 与实现双向一致；
5. 校验页面组件引用闭合、插槽锚点完整；
6. 校验区块定位信息、WXML 片段、组件引用、控制器处理函数与 `uiBlockBlueprint`。

## 7. 扩展流程

### 7.1 新增 Base 内置组件

1. 在 `templates/base/ordering-base/1.0.0/src/components/<id>/` 落盘四件套。
2. 同步 `manifest.json#builtinComponents`、相关页面 `usingComponents` 与 WXML。
3. 在 `curation.v1.json#components.<id>` 写用途、场景、数据字段、约束与示例。
4. 执行重冻结 → `catalog:write` → `catalog:check` → `npm test`。

### 7.2 新增 FrontendPack 页面区块

1. 在视图包 WXML 中保留可定位的 `fp-*` 类名与完整插槽锚点。
2. 在 `curation.v1.json#sections.<packId>@<version>.<pageId>[]` 定义区块 ID、定位器、复用级别与约束。
3. 如果是 `promote-to-ui-block`，必须写 `uiBlockBlueprint`（建议 ID、props、events、提升步骤）。
4. 执行 `catalog:write` → `catalog:check`。

### 7.3 新增可注入组件

1. 按 [`组件入库范例.md`](组件入库范例.md) 新增 Feature Pack 或 UI Block。
2. 登记注册表、重冻结、生成工程并通过微信编译。
3. 执行 `catalog:write`，确认组件卡 `runtime.mode` 为 `slot-injection` 或 `registry-validation`。
4. 不要把 `base-page-fixed` 组件写进 `Plan.components` 期待替换页面。

## 8. 当前已知缺口

| 缺口 | 影响 | 处理 |
| --- | --- | --- |
| `slots.json` 缺少 `menu-hero` | 人类可读镜像与 Base Manifest 不一致；页面卡仍通过回退映射给出 `menuHero` | 下一轮 Base 版本升级时补齐；当前以 Manifest 为准 |
| 3 个 UI Block 与 Base 同名组件共享实现 | `Plan.components` 不会复制它们；卡片标注 `registry-validation` | 不重复建资产；等 Composer 支持组件替换后再评估 |
| 23 个区块中 8 个为 `promote-to-ui-block`（占比最高，另有 8 个 `base-component-use`、4 个 `slot-only`、3 个 `direct-wxml`） | 跨模板复用前需要先提升为 UI Block | 按区块卡 `uiBlockBlueprint` 逐个立项，不在模板生成中顺手生成 JS |
| 区块卡不覆盖 Base 页面原有区块 | 当前只索引 FrontendPack 覆盖的 `home`/`menu` | 后续按需为 Base 8 页增加区块投影 |

## 9. 审查清单

- [ ] `npm run catalog:check` 退出码 0。
- [ ] 组件卡 `interface.props/events` 与源码双向一致。
- [ ] 组件卡 `runtime.mode` 与 Composer 实际行为一致。
- [ ] 页面卡 `declared-only` 组件不被当成可用组件。
- [ ] 布局卡每个插槽的四段锚点各出现一次。
- [ ] 区块卡 `controller.verified=true`，`missing=[]`。
- [ ] `promote-to-ui-block` 区块具有 `uiBlockBlueprint` 与提升步骤。
- [ ] 目录中无绝对路径、密钥、Token、外网 URL。
- [ ] 资产改动后先重冻结注册表，再重生成目录。
