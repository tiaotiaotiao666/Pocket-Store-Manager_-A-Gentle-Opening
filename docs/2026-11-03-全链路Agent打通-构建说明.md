## 0. 一句话结论

**自动化链路已真实打通**：对话 → 模板候选 → 用一句话改模板 → 预览立即变化 → 传图由 Agent 填表 → 用户修改 → 确认 → Composer 导出，这条链路的**纯逻辑段已 41/41 断言跑通**，前端全量 622 例 621 pass、服务端本轮新增 127 例全绿、注册表与小程序门禁通过。

**但端到端验收判 `INCOMPLETE`，不是 PASS**。原因只有两类，都不是本轮代码缺陷：
1. 本机没有 MySQL（3306 未监听），`server` 起不来，真实 HTTP 的 Agent 调用无法执行；
2. Electron 点击、微信开发者工具真实渲染、截图回传属 GUI 人工步骤，本轮未由用户操作。

因此：**不得对外宣称「全链路已人工验收通过」**，只能宣称「自动化链路已打通，等待 1 次人工走查」。

## 2. 关键事实更正（影响后续所有判断）

**旧结论「DeepSeek 无视觉模型」已作废。** 2026-11-03 用 `server/.env` 的 Key 只读实测：

- `GET https://api.deepseek.com/models` → 200，返回两个模型：
  - `deepseek-flash`（`DeepSeek-V4.1-Flash`，`context_window=1048576`，**`input_modalities=["text","image"]`**）
  - `deepseek-v4-pro`（`input_modalities=["text"]`）
- `POST /chat/completions` + `model=deepseek-flash` + OpenAI 多模态 `content: [{type:"text"},{type:"image_url",image_url:{url:"data:image/png;base64,..."}}]` → **HTTP 200，格式被接受**。
- `deepseek-chat` 仍可调用，但响应 `model` 回填为 `deepseek-flash` → **它是别名**。

结论：视觉能力在模型侧已就绪，本轮已把它接进 `agent-turn.v2`；**仍不能生图**（生图必须另配 provider，见第 9 节）。

### 3.1 三条必须记住的实现约束（偏离会直接导致导出失败）

1. **区块落位只写 Plan 顶层 `slotOrder`，禁止改写 `plan.features[].slots[]`**。原因：`poster-carousel` 的 `requiresSlots=['home-hero']`，改写 slotId 会让 Composer 报 `SLOT_REQUIRED_MISSING`。Composer 的做法是「先按原始 slots 校验 requiresSlots，再用 `slotOrder` 目标 slot 作为 assignment key」。
2. `presentationTokens` **只含 `homeHeroSize` / `productCardSize`**；轮播档位不进这里，而是写进 `poster-carousel` 的 `props.size`（`cloneProps` 白名单已放行 `size`）。
3. `SET_STYLE` 只清除 `presentation.patch.theme`，保留 `sizes` / `slotOrder` / `copy`；撤销回到旧模板时必须同时恢复补丁与模板（`restorePresentation()` 已按 `snapshot.build.selectedId` 对齐）。

## 4. 数据流（从对话到导出）

```text
用户在 STORE_INFO 输入/传图
  └─ requestAgentTurn({ images })  ──(有图自动切 v2)──► POST /api/v1/agent/turn
        DeepSeek deepseek-flash 多模态 → 草稿（菜名/价格整数分/描述）
        └─ AGENT_TURN_SUCCESS → AgentDraft（可编辑）→ 用户确认

TEMPLATE_PICK 阶段用户说一句话
  └─ TEMPLATE_REVISE_REQUEST(requestId)
        └─ POST /api/v1/agent/template-revise
             服务端：校验 → 模型出 patch → 合并 basePatch → 再校验 → 服务端重算 changes
        └─ TEMPLATE_REVISE_SUCCESS / FAILURE（晚响应按 requestId 丢弃）
              └─ state.presentation.patch（主题/尺寸/落位/文案）

state.presentation
  └─ planFromSession：theme 覆盖 + presentationTokens + 顶层 slotOrder + carousel props.size
        ├─ previewViewModel：blocks(pageId/size) + sizes(homeHeroPx/productCardPx) + store.tagline
        │     └─ MiniProgramPreview / PreviewTabs / PreviewShared / PosterCarouselBlock（实时刷新 + 可撤销）
        └─ Composer（scripts/composer）：validatePlan → resolve（按 slotOrder 落位）→ emit
              └─ theme.generated.wxss（--store-home-hero-min-height / --store-product-card-min-height）
              └─ config/slots.generated.js（homeHero/homeMarketing/menuAside/menuHero）
              └─ 导出工程 → 微信开发者工具（人工打开 + 编译 + 截图回传）
```

## 7. 验收结论与边界

### 7.1 本轮**能**证明

- 契约层、状态机、预览投影、Composer 导出四段的一致性：同一 Plan 同时驱动预览与导出，尺寸/落位/文案三处都有可执行断言。
- Agent 改模板的安全边界：白名单、`__proto__` 拒绝、8192 字节/深度/键数限制、非法值整包拒绝、无部分应用。
- 图片契约：张数/MIME/base64/单张 400KiB/合计 1MiB，超限整包拒绝且 Provider 不被调用。
- v1 兼容：`agent-turn.v1` 响应字节级语义未变（有测试断言 key 集合）。
- 导出确定性：同一输入两次导出字节完全一致。

### 7.2 本轮**不能**证明

- 桌面端真实点击（模板对比、对话修改、上传、导出、截图回传）。
- 微信开发者工具真实编译与真机渲染，以及「React 预览 vs 真机视觉」一致性。
- 真实 HTTP 的 Agent 调用（v1 文本、v2 视觉、template-revise、template-candidates）——因为本机 MySQL 未启动。
