# 文档中心与维护规范

## 1. 阅读入口

新会话按以下顺序阅读：

1. [`项目概览.md`](项目概览.md)：项目目标、代码现状、工作线和当前顺序。
2. [`handoff/README.md`](handoff/README.md)：选择仍然有效的活动交接。
3. 排查或登记缺陷时读 [`bugs/README.md`](bugs/README.md)。
4. 按任务阅读下表的规划、契约或操作指引。

根目录长文件名需求文档是唯一权威需求来源，保持只读。根目录 `README.md` 只负责项目快速启动，不再承载逐轮构建历史。

## 3. 交接区域

`docs/handoff/` 的结构固定为：

```text
handoff/
├─ README.md             交接索引和编写规则
├─ 当前工作区交接.md      跨工作线的最新接续事实
└─ archive/              已完成或 superseded 的历史摘要
```

当前没有待执行的阶段交接；B0/B1/B2 均已完成。下一阶段（M5 本地 Composer 或 B3）需先由用户批准，再新建活动交接。

直接位于 `handoff/` 的文件必须是仍可执行的活动交接。阶段完成或出现替代交接后，将有效信息压缩到 `archive/YYYY-MM-DD-主题.md`，并更新索引；不要让新会话从多份“上一轮/本轮”中猜测当前状态。

历史摘要只保留当时的决策、真实验证、未解决事项和当前替代关系。已完成的长设计/任务清单不作为当前执行依据。

## 4. 文档产出规则

1. **一个事实一个主位置**：现状写项目概览，未来写规划，字段写契约，环境写指引，接续写交接；其他文档只链接，不复制全文。
2. **明确状态**：使用“已实现 / 部分实现 / 规划 / 历史”及日期。代码不存在时不得写成已完成。
3. **活动文档不用‘本轮’命名**：当前文档以主题命名；日期用于历史摘要和验证记录。
4. **验证写真实结果**：记录命令、通过/失败、未执行项和阻塞，不用笼统“已测试”。
5. **收尾更新活动交接**：写改动文件、执行命令、真实结果、遗留问题和下一步。无需再默认创建“本轮构建介绍”。
6. **删除前先迁移有效信息并修链接**：重复、过时且无历史价值的文档可以删除；有追溯价值的压缩到 archive，不保留多份同义文档。
7. **链接使用相对路径**：移动文件后全仓检索旧文件名，包括 README 和契约文档。
8. **不记录秘密和机器临时状态**：密钥、Token、连接密码不得写入；本机路径仅在有复现价值的指引中保留。
9. **中文为主**：需求、接口、部署和交接使用简体中文，技术名词保留英文原文。

## 5. 不同改动的更新位置

| 改动 | 必须同步 |
| --- | --- |
| 完成或改变里程碑 | 项目概览、待完成目标、相关活动交接 |
| API/订单/权限/金额变化 | api、order-state 或数据模型契约，并评估前端与测试 |
| 桌面状态流或服务边界变化 | 面向AI的桌面端构建文档、项目概览（若现状改变） |
| 小程序组件契约变化 | component-contract、相关组合规划 |
| 模板组合架构或资产发布规则变化 | 模板库与组合生成规划、template-schema、后端待实现接口清单 |
| 环境、启动或部署变化 | backend-local-dev / windows-deployment / wechat 指引 |
| 阶段收尾 | 活动交接；必要时将旧交接归档并更新索引 |

## 6. 最低交付检查

- 新会话能否只从项目概览和活动交接找到下一步？
- 当前实现与规划是否明确分开？
- 是否出现同一状态在多个文档中互相矛盾？
- 所有相对链接是否有效？
- 是否记录真实验证及未解决问题？
- 是否保留用户未提交工作，没有以整理文档为名回滚代码？
