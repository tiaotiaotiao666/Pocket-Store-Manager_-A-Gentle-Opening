## 1. 项目要解决什么

“智能开店 / 口袋店长·轻启”包含一个 Windows 桌面生成器和其生成的微信原生门店小程序。近期业务目标是完成餐饮扫码点餐答辩 MVP，后续目标是通过可验证的模板资产库，让 Agent 按店主需求组合不同小程序模板。

当前首要交付不是模板数量，而是：

```text
运维预置门店与店主
→ 顾客扫码浏览菜单
→ 创建订单
→ 演示模拟付款
→ 店主接单、制作、可取餐、完成
```

真实微信支付、退款、外送、公开店主注册、客户端授权和自动审核发布不在 MVP 范围。

## 5. 关键架构边界

### 桌面端

`App.jsx` 是组合根；组件不直接请求 API、不读取全局业务状态。服务层处理外部能力，reducer 和 domain 保持纯函数。桌面 React 小程序预览只是实时效果预览，不能替代微信运行时验收。

### 小程序

坚持微信原生，不使用 Taro/uni-app。页面组合组件并调用服务层；组件只接收 properties、只发事件，禁止 API、`globalData` 业务状态和固定路由。详见 `docs/component-contract.md`。

### 后端

NestJS 模块化，MySQL 负责业务事实，Redis 负责缓存和按需加速。API 使用 `/api/v1`，金额只用整数分并由服务端计算，门店资源按 `storeId` 隔离，角色只从数据库 membership 获取。

### Agent 与模板

`agent-turn.v1` 只负责资料收集；`agent-turn.v2` 增加受限图片与视觉抽取。2026-11-03 起 Agent 还可输出**白名单展示补丁**（主题色 / 尺寸档位 / 区块落位 / 文案菜品），但仍不能生成任意业务源码、不能增减组件，也不能绕过主题与布局约束；确定性 Composer 从可信版本化资产生成工程，并用 Lock 保证可复现。

## 7. 当前主要风险

- **本机 MySQL 未启动**：`3306`/`6379` 均未监听，`server:dev` 在 Prisma `onModuleInit` 即 `P1001` 退出；服务端 6 个 DB 集成测试与真实 Agent HTTP 调用因此为 `INCOMPLETE`。
- 桌面预览与导出虽已共享 CompositionPlan，但 React 仍是**复刻层**，不得当作微信真机一致；真机一致性需按人工走查清单核对。
- `composer:verify` 的 `PATH_ESCAPE` 为既有缺陷：报告文件内含绝对路径；移出两个报告文件后 8 项全绿。
- 生图通道关闭（`IMAGE_PROVIDER_NAME=not-configured`），导出仍使用 `local-demo` 占位图；本轮只交付提示词约束。
- `presentation` 展示补丁未持久化到 `projectSnapshot`，重开项目后丢失。
- `assets.images` 无删除动作，移除环境照后已写入条目不会回滚。
- Agent 的 Authorization 只检查 Bearer 形式，不是真实店主身份认证；B1 的 `SessionAuthGuard` 尚未接入 Agent。
- B1 的真实微信 `jscode2session` 未用真实凭据验证，且尚无接口限流。
- 微信开发者工具 `proxyType=SYSTEM` 会让 `cli auto` 卡 AppID 校验，需切直连；真机 HTTPS、安全区与性能仍未验证。
- 新导出工程的 `md` 档与改前视觉有差异（海报 300→240rpx、商品图 168→140rpx、store-header 增加 `min-height:190rpx`），需视觉确认。
- M7 的 `direct 2` 只代表「可进店主可选列表」，真机扫码、安全区与海报视觉未验收；不得宣称可直接上架。
- 契约偏差：`Plan.components` 不覆盖 Base 同名组件（`emit.cjs:654-701` 只从 Base 复制，Feature Pack 才按插槽复制），UI Block 目前是登记/校验层资产。见 `docs/evidence/m7/s6.md` §5.1。
- Composer 产物固定 `appid=touristappid`，新版开发者工具会 `APPID_ERROR`；编译需用副本替换 AppID，或走交接向导后置写入。
- ModelArts/盘古未接入；不得将 OpenAI 兼容适配或 DeepSeek 描述为华为云模型接通。
