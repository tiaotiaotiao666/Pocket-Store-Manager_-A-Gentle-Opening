# 桌面生成器云端接口清单（后续阶段）

> 本文覆盖桌面生成器的项目/会话、候选、提示词、生图、部署、模板注册表和组合生成等后续接口，不是点餐业务后端的首期清单。统一路线见 [`后端实现方案与套餐.md`](后端实现方案与套餐.md)，模板组合架构见 [`模板库与组合生成规划.md`](模板库与组合生成规划.md)，顾客/店主 API 契约见 [`api.md`](api.md)。除第 15 节明确标记已实现的 `agent/turn` 外，其余接口均为规划；桌面端当前由本地服务或占位实现支撑。
> 技术栈约定：NestJS 模块化 + MySQL（RDS）+ Redis（DCS），API 使用 `/api/v1` 版本化风格；订单/商品金额以整数「分」存储与传输，金额由服务端计算。

## 1. 通用约定

- Base URL：`/api/v1`，JSON，`camelCase`。
- 认证：店主登录后 `Authorization: Bearer <JWT>`。
- 错误结构：

```json
{ "code": "PROMPT_ROUND_INVALID", "message": "人类可读说明", "details": {} }
```

- 幂等：创建类请求支持 `Idempotency-Key` 头。
- 分页：`page` / `pageSize`，响应 `{ items, page, pageSize, total }`。
- 时间：ISO 8601 字符串。
- 金额：整数分（如 `2800` 表示 28.00 元），前端不传总价。
- 长任务：统一异步任务模型 `{ taskId, status, progress, result?, error? }`，状态 `queued | running | succeeded | failed | canceled`。

### 5.1 模板页「不满意 → 重新用语言描述」的现状与后端方案（2026-11-03）

前端已实现交互闭环（`TEMPLATE_PICK` 页内输入 → 重新匹配 → 原地替换候选），但**候选排序仍是本地确定性规则，不是大模型**：

- 现状：`src/services/agentService.js#buildTemplateCandidates` 按 `selectedFeatures` 定基础顺序与功能匹配分；若存在 `customPrompt`（含模板页累积的 `build.feedback`），按 `src/domain/catalog.mjs#rankTemplatesByBrief` 的关键词命中数重排，命中词回写到候选的 `note` / `briefHits`；识别不到任何风格词时保持功能优先，并在 `note` 里明说「没有可识别的风格词」，不做假装理解。
- 累积的 `build.feedback`（最近 8 条、每条 300 字）随 `project.json` 持久化，重开项目后继续沿用。
- 前端已预留的服务契约：与本节 `POST /api/v1/generation/template-candidates` 完全一致，只需把 `customPrompt` 换成累积描述（用「；」拼接）。接入时**不需要改前端 UI**，只需把 `agentService.buildTemplateCandidates` 换成 HTTP 实现并在返回中保留 `briefKeywords` 字段；缺失该字段时前端自动隐藏「描述命中 n」标签。

后端接入建议（未实现，按优先级）：

1. 请求体在现有 `selectedFeatures` / `customPrompt` 之外补充 `storeBrief`（品类、地址、营业时间）与 `feedbackHistory`（前几轮描述），让模型能看到「用户已经否定过什么」，避免每轮重复推荐同一套骨架。
2. 响应除 `candidates` 外补充 `matchedKeywords: string[]` 与 `reason: string`；服务端必须校验模型返回的 `id` 只能来自模板注册表白名单，禁止模型凭空生成模板 id 或 layout。
3. 失败/超时返回结构化错误（如 `TEMPLATE_MATCH_FAILED`、`TEMPLATE_MATCH_TIMEOUT`），前端已按 `TEMPLATE_REBUILD_FAILED` 处理：保留上一版候选、提示重试、不清空用户输入。
4. 不得在该接口内写业务库；模板候选属于「展示候选」，与 `19.4/19.5` 的 `candidate / baseRevision / turnId` 显式确认边界一致。
5. 若走大模型，仍应保留本地关键词匹配作为「模型不可用时的确定性兜底」，但必须在返回里标注来源（现有 `source` 字段），不能让用户误以为结果来自模型。

验收边界：入口与交互可在桌面端截图验收；「候选来自真实模型」只有在服务端返回 `provider` / `model` 且非本地兜底时才可宣称。

## 10. Redis 用途建议

- 会话当前 phase 与最近消息缓存（降低 MySQL 读压力）。
- 异步任务状态与进度（TTL 与任务生命周期一致）。
- 幂等键（`Idempotency-Key` → 结果）。
- 接口限流（按 owner / IP）。
- SSE 事件通道（如需实时进度）。

## 12. 安全与合规

## 15. Agent 资料收集（`POST /api/v1/agent/turn`）

> 状态：**已实现（真实 Provider：DeepSeek）**。桌面端通过 `VITE_AGENT_TRANSPORT=http` 切换；默认仍为本地 Mock。
> **ModelArts / 盘古尚未接入**；没有 Skill、工具调用、多 Agent、自主规划和自动发布。
> 完整字段、错误码与配置见 [`agent-turn-contract.md`](agent-turn-contract.md)；历史验证记录见 [`handoff/archive/2026-10-31-Agent资料收集与DeepSeek接入.md`](handoff/archive/2026-10-31-Agent资料收集与DeepSeek接入.md)。

### 15.1 能力定位

这是**开店资料收集**能力，不是点餐业务接口，也不是项目/会话持久化接口：

| 对比项 | `agent/turn` | `store-projects` / `generation/*` |
| --- | --- | --- |
| 目的 | 从店主自然语言提取结构化开店资料草稿 | 项目持久化、模板匹配、提示词、生图 |
| 写入 | **店主确认前不写库** | 项目/任务持久化 |
| 身份 | 未来店主鉴权 | 店主鉴权 |
| 会话 | 单轮 `turnId`；不得复用 B1 `sessions` | 项目 ID / 任务 ID |
| 模型 | 只抽取与草拟 | 生图/对话模型 |

禁止把 B1 顾客登录的 `sessions` 表当作 Agent 会话表。若后续需要持久化，应新增 `agent_sessions` / `agent_turns` 独立表并单独立项。

### 15.2 请求与响应

- `POST /api/v1/agent/turn`，JSON，`/api/v1` 版本化。
- 请求：`contractVersion='agent-turn.v1'`、`utterance`（1–500 字）、`draft`（`ContractDraft`）、`client.surface='desktop'`、`client.phase='store-info'`、`projectId=null`。
- 响应：`contractVersion`、`turnId`、`status`（`collecting|reviewing`）、`reply`、`draft`、`missingFields`、`errors`、`nextQuestion`、`meta`。
- 金额只传 `priceCents` 整数分；`priceText` 不进入契约。
- `meta.mock=true` 时必须明确标识未调用真实模型；真实接入后 `meta.mock=false` 且 `meta.model` 为真实模型标识。

## 19. Agent 展示修改与候选身份（`agent-turn.v2` / `agent-template-revise.v1` 已实现；候选身份与会话持久化仍待实现）

> 状态：**仅建议，未实现，未冻结为可用契约。** 当前前端仍使用 `agent-turn.v1`，本节没有对应 Controller、Service、DTO、数据库表或前端 transport。实施前必须另写并评审 v2 契约与测试，不得把 v1 响应静默伪升为 v2。
>
> 建议沿用 `POST /api/v1/agent/turn` 的 API 路径版本，并以 `contractVersion='agent-turn.v2'` / `X-Agent-Contract: agent-turn.v2` 区分 wire contract；也可以评审后选择独立路由，但必须保持 v1 向后兼容。

### 19.1 目标与硬边界

v2 可在已校验草稿之外返回受控 `presentationPatch`，用于调整候选预览的布局和主题展示，并为模板/展示候选提供服务端权威稳定 ID。它不应成为模型执行代码、注入样式或发布业务的通道。

- `presentationPatch` 只影响未确认候选的展示草稿，不直接修改 confirmed 门店、商品、订单或发布状态。
- 模型只能提出候选值；服务端必须重新校验，前端必须再次经过白名单 ViewModel 适配，不得直接 `eval`、动态 import 或把 patch 拼进源码。
- 本地 `project.json` 能保存未确认草稿，不等于后端已写业务库；v2 的显式确认前仍不得写门店/商品业务库或发布。
- 禁止在 patch 中接受任意源码、JavaScript/TypeScript/JSX/HTML、CSS 文本、style 字符串、URL、远程资源地址、文件路径、组件名或 import 指令。未来图片只能走独立的服务端资产 ID 与归属校验，不能把 URL 塞入 patch。

### 19.2 `presentationPatch` 白名单建议

首版建议只允许以下数据形状，`additionalProperties=false`；未列出的键一律拒绝整个 patch，不静默执行部分危险修改：

```json
{
  "presentationPatch": {
    "layout": "menu",
    "theme": {
      "pageBackground": "#FFF8F2",
      "primaryColor": "#C85A2A",
      "accentColor": "#F2A65A",
      "textColor": "#2F2520",
      "tabBarBackground": "#FFFFFF",
      "tabBarColor": "#7A6D66",
      "tabBarSelectedColor": "#C85A2A"
    }
  }
}
```

| 字段 | 建议约束 |
| --- | --- |
| `layout` | 可选枚举：`menu \| catalog \| editorial`；不接受模板源码或自定义布局名 |
| `theme` | 可选对象，只允许表中七个既有 token；不接受 `*Rule`、`backgroundImage` 等额外 CSS 属性 |
| 七个颜色 token | 可选字符串，严格匹配 `#RRGGBB`；服务端规范化后还要通过现有主题对比度/Composition 校验 |
| patch 整体 | 限制深度、键数和序列化大小；数组、原型污染键、未知嵌套对象与非 JSON 值均拒绝 |

`thumbnail` 继续只支持本地固定渐变类型。若未来需要受控图标，也只能使用前后端共享的枚举 ID；不能直接传图标 URL、SVG 字符串或组件引用。

建议错误码：`PRESENTATION_PATCH_INVALID`（422，字段级 details）、`PRESENTATION_THEME_CONTRAST_INVALID`（422）。校验失败时保留上一份已接受展示草稿，不产生部分写入。

### 19.3 候选稳定 ID（服务端权威）

- 候选 ID 由服务端在校验通过后生成，建议 ULID/UUID，数据库唯一；客户端只把它当不透明字符串。
- 不接受模型用数组下标、候选名称、模板名或任意字符串充当权威 ID；不得信任客户端自称的候选归属。
- 服务端保存 `candidateId → projectId/ownerId、Recipe/Base/资产版本、layout、revision、状态` 的映射。重新打开同一候选时 ID 不变；重新生成新候选使用新 ID，删除/撤销后不得复用旧 ID。
- 选择、展示修改、确认和持久化都必须携带 `candidateId`，服务端逐项校验 project/owner 归属、候选状态与资产版本。未知、跨项目或已撤销候选返回 404/409，不得回退到“第一个候选”静默应用。
- 当前 v1 本地 React key 只解决渲染稳定性，不等于服务端候选 ID；二者不得混写。

### 19.4 `baseRevision` / `turnId` 过期规则

建议把并发控制字段放在服务端可控的 turn/候选元数据中，而不是交给模型生成：

- `baseRevision`：客户端发起修改时携带的、最近已读候选/展示草稿版本，整数且单调递增。服务端用事务或条件更新比较当前 revision；不一致返回 409 `AGENT_BASE_REVISION_STALE`，不得覆盖较新的模型结果或人工编辑。
- `revision`：每次成功接受展示草稿、人工编辑或确认后由服务端递增，并随响应返回。前端不得自行计算服务端 revision。
- `turnId`：每个被服务端接受的逻辑 turn 的不透明唯一 ID，由服务端生成并绑定 owner、project、candidate、baseRevision 和最新状态；重试幂等返回原 turn 结果，不重复推进 revision。
- 同一 Agent 会话只有最新有效 `turnId` 可以应用/确认。新 turn 被接受、项目重置/切换、候选撤销或人工编辑使旧 turn 失效后，旧 turn 的晚响应只能作为过期结果处理，不能覆盖当前草稿、候选或 confirmed 状态；确认旧 turn 返回 409 `AGENT_TURN_STALE`。
- 服务端持久化草稿时，应在同一事务内再次检查 `baseRevision` 和最新 `turnId`；仅在请求入口检查不足以防止竞态。
- 可额外设置 turn TTL，但 TTL 只能作为清理手段，不能替代 revision 与最新 turn 校验。
- 前端 v1 的进程内 `requestId` 只负责忽略本地晚响应，与服务端 `turnId`、HTTP 错误 `requestId` / `X-Request-Id` 不是同一字段，v2 不得复用混称。

### 19.5 显式确认与持久化建议

建议区分“保存未确认 Agent 草稿”和“确认写入业务资料”两层：

1. **未确认草稿持久化（可选能力）**：如需跨设备恢复，使用独立 `agent_sessions` / `agent_turns` / 展示草稿与候选表，保存 owner、project、candidate、turn、baseRevision/currentRevision、白名单 patch 和状态；不得复用 B1 `sessions`，也不得借草稿保存写门店/商品业务表。
2. **显式确认**：新增独立确认动作，例如 `POST /api/v1/agent/turns/:turnId/confirm`，请求只携带 `candidateId`、`baseRevision` 等必要字段并支持 `Idempotency-Key`。必须由店主明确点击触发，不能因 turn 返回 `reviewing` 自动确认。
3. **确认时重验**：服务端重新校验 owner、候选归属、最新 turn、revision、完整 ContractDraft、presentationPatch 与资产版本；在事务内完成条件更新和业务写入。重复确认返回同一结果，过期/跨 owner/非法 patch 不落库。
4. **确认不等于发布**：业务资料确认、模板候选确认、导出和微信发布是不同门槛。真实发布仍需独立授权、显式动作和现有小程序审核边界。
5. **本机快照独立**：桌面端继续按既有 `project.json` schema 保存本地未确认草稿和会话；服务端草稿持久化是否上线，不得隐式要求本轮修改 snapshot schema。

金额继续只使用整数 `priceCents`，业务价格与任何总价均由服务端按既有规则校验/计算，前端不传总价。
