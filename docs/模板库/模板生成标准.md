# 模板生成标准

> 本文定义“从店主需求生成一套新的微信小程序模板”的完整标准流程。
> 模板生成的产物是一份 Recipe（`recipe.json` + `plan.json` + `release.json`）以及由 Composer 确定性生成的完整小程序工程，而不是一份新写的业务源码。
> 字段契约以 `templates/registry/schema/composition.v1.json`、`manifest.v1.json`、`base.manifest.v1.json`、`lock.v1.json` 和 `scripts/composer/` 为准。

## 1. 目标与边界

### 1.1 目标

```text
用户文字/图片需求
→ 结构化 UiRequirement
→ 资产能力覆盖检查（CapabilityCoverageReport）
→ RecipeDraft
→ CompositionPlan（精确版本）
→ 确定性 Composer 生成
→ 产物静态校验
→ 微信开发者工具真实编译与核心回归
→ 候选 Recipe / 正式模板
```

### 1.2 必须保持的边界

- Agent 不直接生成或修改 WXML、WXSS、JavaScript。
- Agent 只选择注册表内、已冻结、版本精确的资产。
- 页面控制器与服务层复用 Base 中已验收的实现。
- 新增交互逻辑必须拆成独立的“新资产入库”任务，不能在模板生成流程中顺手放开任意 JS。
- 后端能力未实现时，模板必须被拒绝或标记 `preview-only`；不能伪装成可上线功能。

## 2. 输入契约：先把需求结构化

模板生成请求必须能被机器解析。建议使用以下结构（当前上层 Agent 工作流尚未完整实现，落地时以本结构为准）：

```json
{
  "requestId": "req-20261104-001",
  "utterance": "首页改成大幅海报轮播，保留下单和店主接单",
  "images": [],
  "mustKeep": ["商品详情跳转", "加减购物车", "结算", "订单状态推进"],
  "pages": ["home", "menu", "orders", "mine", "checkout", "order-detail", "product-detail", "merchant-orders"],
  "themePreference": { "primaryColor": "#1F6F54" },
  "sizePreference": { "homeHeroSize": "lg", "productCardSize": "md" },
  "assetNeeds": []
}
```

规则：

1. `mustKeep` 中的业务动作必须能在 Base 控制器/服务层找到对应能力；找不到就拒绝。
2. `pages[]` 必须覆盖 Base Manifest 中 `required: true` 且与目标受众匹配的页面。
3. `images[]` 只能作为视觉参考和素材来源；不能替代已登记的组件契约。
4. 需求里的颜色、尺寸、文案、落位优先映射到 Plan，不应触发源码生成。

## 3. 能力覆盖门禁（核心标准）

### 3.1 资产目录必须统一

生成前必须同时读取：

- Base 内置组件：`templates/base/ordering-base/1.0.0/manifest.json#builtinComponents`
- Registry UI Block：`templates/components/`
- Feature Pack：`templates/features/`
- 页面控制器动作：Base 各页面 `index.js` 的 `methods`
- 服务能力：`templates/base/ordering-base/1.0.0/src/services/`
- 后端 API 契约：`docs/api.md` 或等价的能力清单

只读取其中一部分，会把已有能力误判为“缺失”。

### 3.2 覆盖报告

每次生成前必须输出并校验一份报告：

```json
{
  "requestId": "req-20261104-001",
  "status": "covered",
  "requiredCapabilities": [
    "poster-carousel@1.0.0",
    "product-card@1.0.0",
    "cart-bar@1.0.0",
    "storefront.v1:stores.catalog",
    "storefront.v1:orders.create",
    "controller:menu.addToCart"
  ],
  "missingCapabilities": [],
  "coveredBy": {
    "poster-carousel@1.0.0": "templates/features/poster-carousel/1.0.0",
    "product-card@1.0.0": "templates/components/product-card/1.0.0"
  },
  "confidence": 0.92,
  "risks": ["参考图未提供字号和间距，复现结果为结构近似而非像素级一致"]
}
```

`status` 只能取：

| 值 | 含义 | 后续动作 |
| --- | --- | --- |
| `covered` | 必需能力全部覆盖 | 进入 RecipeDraft |
| `partial` | 只有非必需视觉项缺失 | 必须让用户确认降级项，并在 Plan 的 `degradations[]` 显式登记 |
| `rejected` | 任一必需组件/交互/控制器动作/后端能力缺失 | 立即停止，不生成任何资产或工程 |

**硬规则：`rejected` 时不得调用 Composer、不得写正式目录、不得启动微信编译。**

### 3.3 视觉参考图的边界

上传参考图时，允许模型识别页面分区、近似组件、颜色和大致布局。必须同时输出：

- 未识别区域；
- 低置信度项；
- 无法从图片确定的交互；
- 风险与成本说明。

不得承诺“像素级原样复现”；字体、图标、隐藏手势和运行时单位都可能无法从单图推断。

## 4. RecipeDraft → CompositionPlan

### 4.1 Recipe 目录

```text
templates/recipes/<id>/<version>/
├─ recipe.json       # 配方身份、说明、晋升证据
├─ plan.json         # 生成输入
└─ release.json      # 发布审核记录
```

### 4.2 `recipe.json`

```json
{
  "schemaVersion": "recipe.v1",
  "identity": { "id": "order-warm-poster", "version": "1.0.0" },
  "planRef": "plan.json",
  "displayName": "暖橙海报点餐",
  "description": "在经典点餐基线上，用海报轮播替换首页门店头部。",
  "recipe": {
    "stage": "candidate",
    "verifiedAt": null,
    "wechatCompile": "not-run",
    "regression": "not-run",
    "secretScan": "pass",
    "approvals": [],
    "knownLimits": ["演示海报为色块素材，未含摄影图片"]
  }
}
```

### 4.3 `plan.json` 必填字段

Plan 是 Composer 的唯一输入，必须包含：

```json
{
  "schemaVersion": "composition.v1",
  "planId": "order-warm-poster",
  "planVersion": "1.0.0",
  "baseTemplate": { "id": "ordering-base", "version": "1.0.0" },
  "registryVersion": "2026.11.0",
  "pages": [
    { "pageId": "home" },
    { "pageId": "menu" },
    { "pageId": "orders" },
    { "pageId": "mine" },
    { "pageId": "checkout" },
    { "pageId": "order-detail" },
    { "pageId": "product-detail" },
    { "pageId": "merchant-orders" }
  ],
  "features": [],
  "components": [],
  "themeTokens": {
    "pageBackground": "#F7F3EC",
    "primaryColor": "#B34A0F",
    "accentColor": "#9C2E12",
    "textColor": "#232323"
  },
  "apiBinding": { "contract": "storefront.v1" },
  "storeProfile": { "name": "柑橘小馆" },
  "previewOnlyAck": false,
  "degradations": []
}
```

当前 `validatePlan` 还会拒绝下列禁止键：`source`、`code`、`script`、`command`、`url`、`token`、`secret`、`password`、`apiKey`、`priceText`、`totalCents`。

### 4.4 可选展示字段

- `presentationTokens`：只允许 `homeHeroSize`、`productCardSize`，值为 `sm | md | lg`，缺省按 `md`。尺寸不要写进 `themeTokens`。
- `slotOrder`：只允许 `featureId`、`pageId`、`slotId` 三键；必须是当前 `features[]` 中每个 `featureId` 的完整排列；目标组合来自 `home-hero`、`home-marketing`、`menu-aside`、`menu-hero`，且不能重复。
- `frontendPack`：可选，只允许 `{ id, version }` 精确引用已登记的 `frontend-pack` 资产。它覆盖指定页面的 WXML/WXSS/页面 JSON，页面 JS 仍来自 Base；详细规则见 [`FrontendPack视图包标准与范例.md`](FrontendPack视图包标准与范例.md)。

`slotOrder` 只改变导出落位的 assignment key；`features[].slots[]` 保持 Recipe 原样，`requiresSlots` 仍按原始声明校验。`frontendPack` 进入 `planDigest` 与 `composition.lock.json`，但不计入业务 `capabilitySet`。

### 4.5 Feature 引用示例

```json
{
  "id": "poster-carousel",
  "version": "1.0.0",
  "slots": [
    {
      "slotId": "home-hero",
      "pageId": "home",
      "dataKey": "homeHero",
      "props": {
        "items": [{ "id": "poster-1", "title": "秋日暖锅上新", "tone": "warm" }],
        "autoplay": true,
        "interval": 4000,
        "showIndicator": true,
        "size": "md"
      }
    }
  ]
}
```

## 5. 主题与尺寸 Token

### 5.1 主题 Token

- 唯一颜色事实是 `themeTokens`，至少四个必填：`pageBackground`、`primaryColor`、`accentColor`、`textColor`。
- 颜色必须是 `#RRGGBB`，大写十六进制。
- 对比度门禁：`textColor` ≥ 4.5，`primaryColor` ≥ 3.0，`accentColor` ≥ 3.0（相对 `pageBackground`）。
- 可选 tabBar Token：`tabBarBackground`、`tabBarColor`、`tabBarSelectedColor`；缺省由 Composer 补齐。

### 5.2 尺寸 Token

尺寸唯一事实：`templates/presentation/size-tokens.v1.json`。

| 组 | sm | md | lg |
| --- | --- | --- | --- |
| `homeHero` | 150rpx | 190rpx | 250rpx |
| `productCard` | 110rpx | 140rpx | 180rpx |
| `carousel` | 200rpx | 240rpx | 310rpx |

- 导出工程只写 rpx；React 预览消费同名 px 值。
- 海报的 `carousel` 档位通过 `props.size` 传入，不写入 `presentationTokens`，避免双写。

## 6. 确定性 Composer

Composer 入口：`scripts/composer/index.cjs`，流水线固定为 P0–P8：

| 阶段 | 名称 | 职责 |
| --- | --- | --- |
| P0 | 契约校验 | `validatePlan`；检查白名单、尺寸档位、`slotOrder`、金额与 JSON 大小 |
| P1 | 注册表冻结 | `loadRegistry({ verifyFreeze: true })`；校验索引、摘要、Manifest、入口与预览数据 |
| P2 | 组合解析 | 精确版本、依赖、冲突、循环、页面、插槽、props 兼容、FrontendPack 页面/锚点与主题对比度 |
| P3 | 生成锁 | 固定 Base/资产/FrontendPack/Composer/API 契约与源文件摘要 |
| P4 | 目录预检 | 父目录、目标目录、路径长度和体积预检 |
| P5 | 生成工程 | 复制 Base，叠加 FrontendPack 视图，写入 `app.json`、主题、插槽配置、公开门店配置和组件 |
| P6 | 产物校验 | 页面四件套、`usingComponents`、动态组件、静态检查、安全扫描与媒体清单 |
| P7 | 原子提交 | staging → 最终目录；失败清理半成品 |
| P8 | 生成报告 | 写 `generation-report.json` 与 `生成报告.md` |

命令：

```powershell
npm run composer:build -- --plan templates/recipes/<id>/<version>/plan.json --out <工作区外的父目录> --mode development
```

`--out` 是父目录，工程名默认取 `planId`，也可以用 `--project-name` 覆盖。生产模式必须提供 HTTPS `api.baseUrl` 与真实版本号，否则 `VERSION_GAP_REQUIRED`。

## 7. 产物与校验

一个成功的导出工程至少包含：

```text
app.js / app.json / app.wxss / sitemap.json / theme.generated.wxss
project.config.json
config/{env.js,slots.generated.js,store.generated.js}
pages/<pageId>/index.{js,json,wxml,wxss}
components/<assetId>/index.{js,json,wxml,wxss}
composition.lock.json
generation-report.json / 生成报告.md
```

生成后必须执行：

```powershell
npm run composer:verify -- --root <生成工程目录> --mode development
npm run mini:check -- --root <生成工程目录>
npm test
```

校验标准：

- `composer:verify` 依次检查页面四件套、`app.json` 与磁盘一致、`usingComponents`、动态加载、静态结构、安全扫描、媒体清单和可复现性。
- `mini:check` 必须 0 错误 0 警告。
- 相同 Plan + 相同注册表重复生成，`composition.lock.json` 的 `lockDigest` 与 `outputDigest.tree` 必须一致。
- 已知缺陷：当前 `composer:verify` 会把产物内 `generation-report.json` 与 `生成报告.md` 中的绝对 `projectPath` 判为 `PATH_ESCAPE`。如果失败明细只包含这两处，先按既有缺陷处理，不要误判为组件问题。

## 8. 预览与发布标准

### 8.1 模板概览图

- 正式 Recipe 的模板卡片应显示预先用微信开发者工具真实渲染并截图的静态图片，而不是 React 复刻预览。
- 概览图必须绑定 Recipe、版本、主题、路由、模拟器尺寸、基础库和数据版本；源码或主题变化后旧图立即标记过期。
- 新候选 Recipe 在第一次真实预览成功之前不生成正式概览图。

### 8.2 当前项目预览

- 应用内预览只作为“效果预览”，用于快速反馈，不能替代微信运行时验收。
- 微信预览应由按键触发：生成受管预览工程 → 写入有效 AppID → 编译 → 读回 `buildId` 校验 → 截图。
- 每次修改应使用固定受管预览目录，而不是重复导出新工程；同一项目单飞，失败保留上一版可用结果。

### 8.3 发布状态

| 状态 | 用途 | 要求 |
| --- | --- | --- |
| `candidate` | 内部候选 | Manifest/Plan/预览数据通过静态校验 |
| `direct` | 店主可选正式模板 | `wechatCompile`、`regression`、`secretScan` 均 `pass`，且有审核记录 |
| `preview-only` | 仅展示能力 | 后端能力缺失，登记到 `preview-registry.json` |
| `expired` | 过期资产 | 不再可选，保留追溯信息 |

## 9. 拒绝规则（必须硬失败）

出现以下任一情况，生成流程必须返回 `rejected` 并停止：

1. 需要新增组件类型，但 Registry 中没有对应已冻结资产。
2. 需要新增页面或页面级交互，但 Base 中没有对应控制器/插槽。
3. 需要新的后端接口、权限、支付、退款、外送、优惠券、会员或营销能力，但后端契约不存在。
4. Plan 出现禁止键、非精确版本、非法颜色/尺寸/`slotOrder`。
5. 资产摘要漂移或注册表未冻结。
6. `preview-only` 资产未确认或试图进入正式 Recipe。

拒绝时应返回：`missingCapabilities[]`、`reason`、`risk`、`nextStep`，而不是生成一个空壳页面。

## 10. 变更管理

- 新增组件：先在 `templates/components` 或 `templates/features` 落盘并验收，再登记到 `registry.v1.json`，执行 `registry:check --write`。
- 新增 Recipe：先以 `candidate` 落盘，真实生成工程并完成微信编译，再补 `recipe.json#recipe.approvals` 和 `release.json`。
- 修改 Base 插槽：属于 Base 版本升级，必须同步 `manifest.json`、`slots.json`、页面锚点和注册表摘要。
- 并行实施时，不要各自修改 `registry.lock.json`；统一由一次冻结操作完成。
- 每次结构或主题变化都要登记证据路径，旧截图不得继续作为当前版本的验收依据。

## 11. 当前实现状态

- Base、UI Block、Feature Pack、Recipe 与确定性 Composer 已实现并冻结。
- 桌面端已接通受管导出与真实截图回传面板；Electron、微信开发者工具的真实人工走查仍待执行。
- `template-revise` / `template-candidates` 已接 DeepSeek 真实调用；但候选仍存在 `meta.degraded=true` 的本地规则降级路径。
- 生图 provider 当前是 `not-configured`，只能输出诚实标注的占位图与提示词，不代表已经接入生图模型。
- `presentation` 补丁尚未持久化；重开项目后已接受的展示补丁会丢失。
