## 1. 这轮交付了什么

`server/src` 从「只有 health/readyz + agent + generation」扩展为完整的点餐业务后端：

```text
src/
  common/    统一错误体、requestId、ID 生成、ValidationPipe、会话 Guard、门店成员 Guard
  auth/      微信/demo 登录、/auth/me、opaque session
  stores/    公开门店
  catalog/   公开目录 + 缓存 + 目录失效
  orders/    状态机、DTO、创建/付款/取消/列表/详情、订单投影
  merchant/  店主订单台、状态推进、商品上下架、店主商品列表
```

模块装配在 `src/app.module.ts`，全局能力通过 `APP_PIPE` / `APP_FILTER` / `APP_INTERCEPTOR` 注册，因此 `main.ts` 与测试启动方式完全一致。

## 2. 端口到数据库的调用链

```text
Controller → Service → PrismaService / CacheService
```

- Controller 只做 HTTP 映射、取当前用户、设置状态码；不写业务规则。
- Guard 只做鉴权与门店成员校验；业务错误通过 `AppError` 抛出。
- Service 负责事务、状态机、计价与幂等。
- Prisma 统一在 `server/src/database/prisma.service.ts`，MySQL 是唯一事实来源；缓存只加速公开目录。

## 3. 关键实现约定（修改前必须知道）

### 3.1 统一错误体

所有非 Agent 路由的错误都经过 `src/common/http/all-exceptions.filter.ts`，输出：

```json
{ "code": "TABLE_REQUIRED", "message": "堂食订单必须提供桌号。", "requestId": "req_...", "details": {} }
```

- `X-Request-Id` 响应头与 `requestId` 始终一致；成功响应由 `RequestContextInterceptor` 写入。
- 不返回堆栈、SQL、OpenID 或密钥。
- `ValidationPipe` 的失败统一映射为 `422 VALIDATION_ERROR`，`details.fields` 列出字段路径。
- Agent 路由仍使用自己的 `AgentExceptionFilter`，保持 `agent-turn.v1` 语义，不被全局过滤器改写。

### 3.2 主键长度

`backend-data-model.md` 曾写「`<prefix>_<26位>`」，但 schema 是 `CHAR(26)`。实现按**总长 26** 生成：`<3字母前缀>_<22位>`，其中前 10 位为时间戳（Crockford Base32）、其余为随机位。见 `src/common/ids.ts`。不要改成 30 位，否则会与已有迁移冲突。

### 3.3 会话鉴权

- Token = `randomBytes(32).toString('base64url')`，数据库只存 `sha256(token)`。
- `SessionAuthGuard` 查 `sessions` 并校验 `expiresAt`；缺失 Token → `401 AUTH_REQUIRED`，格式错误/不存在/过期 → `401 AUTH_INVALID`。
- 角色只来自 `store_members`，不接受客户端声明。
- 路径参数 `storeId` 由 `StoreMemberGuard` 校验：门店不存在 404，非成员 403。
- 订单/商品类路由（无 `:storeId` 路径）由 Service 先解析资源归属，再查 membership；跨店返回 403，资源不存在返回 404。

### 3.4 环境变量优先级

`validateEnv` 现在让**真实进程环境变量优先于 `.env` 文件**。这是为了修复测试与容器部署中 `.env` 静默覆盖 `CACHE_DRIVER` / `NODE_ENV` 的问题。若新增配置项，继续沿用该顺序。

### 3.5 目录缓存

- 键：`catalog:{storeId}`，TTL 300 秒。
- 缓存内容是完整公开目录 JSON（含 `version`、`updatedAt`）。
- 商品上下架在事务内 `catalogVersion + 1`，**提交后**调用 `CatalogService.invalidate`。
- 公开目录只返回 `available=true`；店主商品列表不过滤、不读缓存、不返回 `version`。

### 3.6 订单创建

单事务内依次完成：

1. 门店存在与履约开关校验。
2. 堂食桌号必填且属于本店；自取强制 `tableId=null`。
3. 合并重复 `productId`，合并后数量必须在 1–99。
4. 读取本店商品并过滤 `available=false`，缺失与停售统一返回 `409 PRODUCT_UNAVAILABLE`。
5. 以数据库单价计算 `lineTotalCents` / `totalCents`，保存商品名与单价快照。
6. 写 `orders`、`order_items`、首条 `order_status_logs`、`idempotency_keys`。

幂等：

- 位置：`Idempotency-Key` 请求头，8–128 位可见 ASCII；缺失或非法 → `400 BAD_REQUEST`。
- 唯一键：`(userId, storeId, key)`；指纹是规范化 payload 的 SHA-256。
- 指纹一致返回原订单（HTTP 200，`created=false`）；不一致 `409 IDEMPOTENCY_CONFLICT`。
- 并发唯一冲突（Prisma `P2002`）会回查并按同样规则返回，不会产生第二条订单。

### 3.7 状态机

唯一事实来源是 `docs/order-state.md`，代码在 `src/orders/order-state.ts`：

- 顾客：`PENDING_PAYMENT → PENDING_ACCEPT`（模拟付款）、`PENDING_PAYMENT → CANCELLED`。
- 店主：`PENDING_ACCEPT → PREPARING | CANCELLED`、`PREPARING → READY | CANCELLED`、`READY → COMPLETED | CANCELLED`。
- 店主处理 `PENDING_PAYMENT` 一律 `409 MERCHANT_CANNOT_HANDLE_UNPAID`，优先于矩阵判断。
- 状态更新使用 `updateMany({ where: { id, status: expected } })`；0 行受影响 → `409 STATUS_CONFLICT`。
- 每次成功变更在同一事务写一条 `order_status_logs`；失败不写。
- 模拟付款与顾客取消都是幂等的：已经达到目标状态直接返回当前订单，不重复写日志。

## 5. 测试架构

`server/test/`：

| 文件 | 覆盖 |
| --- | --- |
| `b1-public-auth.test.ts` | 健康检查、公开门店/目录、登录、me、401 |
| `b1-orders.test.ts` | S1–S6、计价、合并、幂等、列表/详情/取消 |
| `b1-merchant.test.ts` | S7–S10、S12、店主列表、上下架、跨店 |
| `b1-production.test.ts` | S11：生产拒绝 demo 登录与模拟付款 |
| `order-state.test.ts` | 状态机纯函数 |
| `agent*.test.ts`、`deepseek*.test.ts` | 既有 Agent / Provider 测试 |

测试辅助 `test/helpers/b1-fixtures.ts` 的关键点：

- 使用**真实 MySQL 测试库**（`TEST_DATABASE_URL`，默认 `smart_store_test`），不 mock Prisma。
- 会先创建测试库、执行 `prisma migrate deploy`，然后清库并写入固定门店/商品/桌号/用户。
- 测试库名必须包含 `test`，否则 helper 直接拒绝执行，避免误清生产库。
- `CACHE_DRIVER=memory`，不依赖 Redis。
- `AppModule` 使用**动态 `import()`**：`ConfigModule.forRoot` 在模块求值时读取环境变量，必须晚于测试里的环境准备；不要改回顶层静态导入，否则测试会读到 `.env` 的 `CACHE_DRIVER=redis` 并在无 Redis 环境启动失败。
- `vitest.config.mts` 设 `fileParallelism: false`：多个测试文件共用同一个测试库，必须串行，避免互相清库。

命令：

```bash
cd server
npm run build
npm test
```

## 7. 尚未完成 / 边界

- B2 未开始：`miniprogram/` 仍是骨架，没有 service 层与真实页面数据。
- 真实微信登录（`jscode2session`）只有代码路径与 fetch 注入边界，未用真实 `WECHAT_APP_ID/SECRET` 验证。
- `GET /orders/:id` 的成员判断是逐次查询，未做缓存或批量优化。
- 没有限流（`429 RATE_LIMITED` 只有错误码契约，没有中间件）。
- Agent 的 Authorization 仍是独立简化 Guard，没有复用 B1 的 `SessionAuthGuard`。
- 本地 `smart_store` 库保留了本轮联调生成的订单；如需干净演示库，应由运维流程清空订单表后重新导入种子，仓库脚本不会自动清业务数据。
