# 智能开店核心闭环重构计划（业务优先）

> 版本：v1.0　日期：2026-11-17
> 依据：docs/审计报告-核心闭环与代码取舍.md、docs/frontend-reconstruct-contract.md、AGENTS.md
> 目标：先跑通“图片 + 描述 → 候选 → 微信预览 → 对比 → 采用/撤销 → 导出”，再清理历史代码。

## 1. 用户要求、仓库约束与审计建议

### 用户要求

- 减少防御性编程，先跑通基本业务。
- 根据审计证据作取舍，不逐条照搬。
- 提供完整可执行的重构计划。
- 前端由其他模型实现，本计划要给出稳定的前端接口。

### 仓库硬约束

审计报告是只读证据与建议，不会覆盖用户要求或仓库约束。AGENTS.md 和 frontend-reconstruct.v1 契约继续有效：

- 模型只产出有界 frontend-pack-draft.v1 JSON DSL，不产任意 WXML/WXSS/JS/WXS、命令、路径或 URL。
- 候选只写应用私有 userData/projects/<projectId>/frontend-runs/...；不写正式 templates/**，不手改 miniprogram/。
- miniprogram/ 是只读镜像；Composer 导出目录才是交付物。
- 真实微信证据缺失时如实显示 BLOCKED、NOT_RUN 或 partial；React 预览不能冒充微信截图。
- 过程卡不展示源码、base64、完整 prompt、密钥或本机绝对路径。
- 继续使用固定入口 npm run frontend:verify，不新增任意命令执行入口。

这些是不可绕过的边界；边界内应减少重复校验和空泛兜底。

### 对审计建议的决定

| 建议 | 决定 | 说明 |
| --- | --- | --- |
| 保留 DSL、renderer、私有 workspace/overlay、dry-run、verify-runtime、采用/撤销 | 接受 | 这是现成的受控交付链，保留并接通。 |
| 修打包、统一微信 CLI、交互失败参与总状态 | P0 接受 | 当前 UI 可能把关键交互失败显示为通过，必须先纠正。 |
| 把微信截图送到候选面板，形成改前/改后 | P1 接受 | 截图已落盘，优先做 IPC 与 UI 接线。 |
| 统一图文输入、重排流程、常驻预览入口、右栏增加对话 | P2 接受 | 用户始终围绕当前项目版本工作。 |
| 立即删除 screen-reference.v1 | 调整 | 先退出新任务入口，保留旧快照只读兼容。 |
| 功能勾选、假构建、模板匹配、生图/Prompt Studio 位于主流程 | 退出主线 | 不影响首要闭环，后续可作为可选工具。 |
| 立刻拆分巨型组件、删所有旧 IPC、同时修基线门禁 | 延后 | 闭环稳定后逐项拆分，减少并行改动和回归范围。 |
| 以更多兜底、重试、默认值来“增强健壮性” | 不接受 | 缺少项目身份或微信证据时应明确失败，不能靠伪上下文掩盖。 |

## 2. 目标业务与范围

### MVP 主流程

~~~
创建/打开项目
→ 收集会影响生成/下单的最小门店资料（非必填可跳过）
→ 同一个输入区上传 1 张参考图并写一句话
→ Agent 基于当前项目版本生成受控候选
→ Composer dry-run
→ 微信开发者工具预览/验证
→ 同路由、同尺寸显示改前/改后微信截图与字段 diff
→ 采用候选或撤销回上一个版本
→ 从当前版本导出 Composer 工程
~~~

首屏提供图片 + 描述入口。门店资料按缺失项在对话中补齐，不再强迫用户先经过功能选择、假构建、模板匹配、生图等阶段。

### 明确暂缓

不接生图 provider、不做像素相似度评分、不推断支付/订单规则或隐藏交互、不扩展 home/menu 以外页面、不做云端多设备同步、不建设第二条图片识别主链。

### 版本原则

版本不可变，采用/撤销只移动当前指针：

~~~
Base → v1 → v2（当前）
       └────仍可回看，不能原地覆盖
~~~

一个项目版本历史作为唯一真相，保存版本 ID、父版本、候选引用、输入摘要、diff、dry-run/微信验证状态、截图索引和时间。Undo/Redo 都移动版本指针，不再各自维护候选、展示补丁和旧截图三套历史。

## 3. 架构职责与简化原则

~~~
React 页面与 hooks
  → frontendReconstructApi（前端唯一 facade）
  → preload 白名单 API
  → Electron 主进程：项目/版本、私有 workspace、Composer、微信验证、截图读取
  → 固定 scripts/wechat-devtools-run.cjs

NestJS frontend-reconstruct.v1
  → 校验、可信能力事实、视觉需求、受控 DSL
~~~

- React 展示状态、收集输入、发用户动作；不读文件、不拼 IPC、不调用 shell。
- facade 是其他前端模型的唯一依赖面；preload 内部 channel 可调整。
- 主进程负责项目版本、候选物化、dry-run、微信验证、证据和采用/撤销。
- 服务端负责请求/能力/DSL，不写仓库源码、不物化本机候选。

### 防御性编程收缩

只保留与外部输入、项目/路径隔离、DSL/Composer 完整性、真实证据真实性有关的校验。内部使用一个明确 DTO，不在多层重复默认空对象、字段重映射和重复判空。禁止 unscoped-project 伪 ID；缺 projectId 返回可读的 PROJECT_CONTEXT_REQUIRED。 不做假进度和自动无限重试；不把 partial/BLOCKED 转成成功。前端不另存一份候选真相。未支持能力统一返回结构化 UNSUPPORTED，不为未来猜测加分支。

## 4. 前端交接接口

以下是 renderer-facing facade 的稳定形状。实际实现可由桌面层适配既有 IPC 与领域状态，但组件不直接依赖 IPC channel。

### 4.1 Facade

~~~ts
type FrontendReconstructApi = {
  getProjectSnapshot(input: { projectId: string }): Promise<ProjectSnapshot>;
  submitTurn(input: SubmitFrontendTurn): Promise<FrontendRunStarted>;
  subscribeProgress(input: { runId: string }, listener: (event: ProgressEvent) => void): () => void;
  getRun(input: { projectId: string; runId: string }): Promise<FrontendRun>;
  readScreenshot(input: ScreenshotRequest): Promise<ScreenshotBytes | ScreenshotUnavailable>;
  launchPreview(input: { projectId: string; versionId: string }): Promise<PreviewResult>;
  verifyRun(input: { projectId: string; runId: string; attempt: number }): Promise<VerificationReport>;
  adopt(input: { projectId: string; versionId: string }): Promise<ProjectSnapshot>;
  undo(input: { projectId: string }): Promise<ProjectSnapshot>;
  redo(input: { projectId: string }): Promise<ProjectSnapshot>;
};
~~~

建议经 window.smartStore.frontendReconstruct 暴露；组件通过 prop/hook 注入，不直接读取其他 window API。

### 4.2 候选请求

frontend-reconstruct.v1 已冻结且拒绝未知字段，不能把项目版本和门店摘要静默塞进 v1。P2 先定义并冻结 frontend-reconstruct.v2；v1 保持兼容读取。前端 facade 接收 v2 DTO，由桌面适配层负责调用后端 v2。

~~~ts
type SubmitFrontendTurn = {
  contractVersion: 'frontend-reconstruct.v2';
  requestId: string;
  utterance?: string;
  images: [{
    kind: 'reference';
    mediaType: 'image/jpeg' | 'image/png' | 'image/webp';
    dataBase64: string;
  }];
  targetPages: Array<'home' | 'menu'>;
  current: {
    baseTemplate: { id: 'ordering-base'; version: string };
    frontendPack: { id: string; version: string } | null;
    presentationPatch: Record<string, unknown>;
  };
  projectVersion: { versionId: string; digest: string };
  storeContext: StoreContextSummary;
  client: { surface: 'desktop'; phase: 'project-agent' };
  projectId: string;
};

type StoreContextSummary = {
  // Freeze the exact allow-listed fields against the existing store draft schema in P2.
  fields: Record<string, string | number | boolean | null>;
  missingRequiredFields: string[];
};
~~~

项目创建时分配真实 projectId；P2 UI 不提交 null。StoreContextSummary 的字段必须按现有 StoreDraft 白名单冻结，不能把任意对象透传。每次请求携带当前已采用的 FrontendPack、presentationPatch、项目版本身份和门店资料摘要，语义是“在当前版本上修改”。

### 4.3 UI 归一状态与运行对象

Facade 将既有领域/IPC 状态映射为稳定 UI 状态，不要求服务端更改已冻结契约：

~~~ts
type RunStatus =
  | 'idle' | 'collecting' | 'planned' | 'materializing' | 'dry-run'
  | 'ready-for-runtime' | 'verifying' | 'ready' | 'partial'
  | 'rejected' | 'failed' | 'blocked' | 'not-run';

type FrontendRun = {
  runId: string;
  projectId: string;
  attempt: number;
  status: RunStatus;
  versionId: string;
  input: { utterance: string; imageName?: string; targetPages: Array<'home' | 'menu'> };
  current: {
    baseTemplate: { id: string; version: string };
    frontendPack: { id: string; version: string } | null;
  };
  coverage: { status: 'covered' | 'partial' | 'rejected'; missing: string[] };
  dryRun: { status: 'PASS' | 'FAIL' | 'BLOCKED' | 'NOT_RUN'; files: number; errors: Issue[] };
  runtime: VerificationReport | null;
  diff: DiffItem[];
  screenshots: ScreenshotRef[];
  createdAt: string;
};
~~~

ready 才能显示通过；partial、blocked、not-run 不能显示成功。失败不自动重试，由用户明确重试。

### 4.4 进度事件

~~~ts
type ProgressEvent = {
  runId: string;
  attempt: number;
  phase: 'request' | 'plan' | 'materialize' | 'dry-run' | 'runtime' | 'persist';
  status: 'started' | 'completed' | 'failed' | 'blocked';
  message: string;       // 受控短文案
  elapsedMs: number;
};
~~~

事件不包含源码、prompt、密钥、base64 或绝对路径。无真实事件时只显示状态文案，不显示百分比假动画。

### 4.5 截图和 diff

~~~ts
type ScreenshotRequest = {
  projectId: string;
  versionId: string;
  route: 'home' | 'menu';
  side: 'before' | 'after';
};

type ScreenshotBytes = {
  runId: string;
  attempt: number;
  route: 'home' | 'menu';
  side: 'before' | 'after';
  mimeType: 'image/png';
  bytes: Uint8Array;
  width: number;
  height: number;
};
type ScreenshotUnavailable = {
  status: 'NOT_RUN' | 'BLOCKED' | 'MISSING';
  reason: string;
};

type DiffItem = {
  field: 'theme' | 'size' | 'slot-order' | 'text' | 'component';
  path: string;
  before: string | number | null;
  after: string | number | null;
};

type ScreenshotRef = {
  runId: string;
  attempt: number;
  route: 'home' | 'menu';
  width: number;
  height: number;
};
~~~

IPC 按 project/version/route/side 查询受信版本记录，再从其私有证据引用读取 attempt 文件，向 renderer 返回字节，不返回路径、不暴露任意读盘。before 默认取该版本的父版本（可切 Base）；before/after 必须同 route、同尺寸，并展示各自 runId、attempt 和状态。React 用短生命周期 Blob URL，切版本或卸载时释放。缺图显示原因，不用 React 图像补位。

### 4.6 项目版本与验证

~~~ts
type ProjectSnapshot = {
  projectId: string;
  currentVersionId: string;
  versions: ProjectVersion[];
  storeDraft: Record<string, unknown>;
};

type ProjectVersion = {
  versionId: string;
  label: string;
  parentVersionId: string | null;
  source: 'base' | 'frontend-candidate';
  runId?: string;
  adopted: boolean;
  diff: DiffItem[];
  verification: 'NOT_RUN' | 'BLOCKED' | 'FAIL' | 'PASS' | 'PARTIAL';
  createdAt: string;
};

type VerificationReport = {
  status: 'PASS' | 'FAIL' | 'BLOCKED' | 'NOT_RUN';
  pages: Array<{ route: 'home' | 'menu'; status: 'PASS' | 'FAIL' | 'BLOCKED'; screenshot?: ScreenshotRef }>;
  interactions: Array<{ id: string; status: 'PASS' | 'FAIL' | 'BLOCKED'; message: string }>;
  tool: string;
  elapsedMs: number;
};
~~~

总体微信状态必须由页面与关键交互共同决定；关键下单动作失败即总体 FAIL，工具不可用是 BLOCKED。采用/撤销/redo/导出都按当前版本指针执行。

## 5. 实施阶段

### P0：跑通执行链（约 1–2 天，不改主 UI）

1. 将 scripts/wechat-devtools-run.cjs 加入 build.files。
2. 将 miniprogram-automator 从 devDependency 改为生产运行依赖，确保安装包包含验证所需模块；打包检查明确断言脚本与依赖在包内。若模块确实不可用，返回明确 BLOCKED。
3. 抽共享 resolveDevtoolsCli()，预览和候选验证复用相同搜索顺序、工程身份检查和错误语义。
4. 页面与 interactions 一起计算总状态；关键下单动作失败不能 PASS。
5. 重新打包并在安装版实测；旧 release 目录不作为证明。

验收：安装版能得到真实 PASS/FAIL/BLOCKED；构造交互失败用例不可能 PASS；CLI 缺失明确 BLOCKED。

### P1：显示真实微信对比（约 3–5 天）

1. 保存截图索引并加受限 IPC 截图读取。
2. 对上一个已采用版本执行 before 截图；候选 dry-run 成功后执行 after 截图。
3. 候选面板变成版本卡：状态、并排截图、字段 diff、采用/撤销。
4. 缺图显示 NOT_RUN/BLOCKED/MISSING 与原因。
5. 覆盖截图路径隔离、route/尺寸配对、关键交互状态的测试。

验收：home/menu 可按同路由同尺寸展示真实微信前后图；身份不匹配拒绝配对；缺任一侧不伪装完成。

### P2：收敛到项目 Agent（约 1–2 周）

1. 定义 frontend-reconstruct.v2 请求/响应和 StoreContextSummary 白名单测试；保持 v1 兼容，不原地扩字段。
2. 项目创建时分配真实 projectId；候选请求携带当前版本与资料摘要。
3. 统一图文 Composer，图片和文字一次提交；取消各 phase 下同一输入执行不同动作的语义。
4. 流程调整为“项目 → 最小资料 → 图片定制 → 预览对比 → 采用/导出”，可选能力不驱动构建。
5. 右栏提供“项目信息 / Agent 对话”切换；对话按项目归属，版本作标记。
6. Composer 区常驻微信预览入口，明确区分未安装、未构建、启动中、已打开、失败。
7. 真实 progress 驱动状态；去掉 94% 假动画；按钮明确为“生成候选”或“跳过定制”。

验收：所有阶段的同一输入只表示修改当前项目；重开项目可看到版本和对话；缺字段时只问必要问题。

### P3：统一版本历史、撤销与导出（约 3–5 天）

1. 项目快照保存版本列表、presentationPatch、候选引用、diff 与验证证据。
2. 键盘 Ctrl+Z、按钮 undo、redo 调用同一版本历史 API。
3. overlay 缺失/摘要漂移时明确阻止当前版本采用或导出，不回落 Base 冒充。
4. Composer 导出使用当前版本的同一 overlay。

验收：重开后历史可回看；撤销后 redo 成功；导出与当前版本一致。

### P4：稳定后清理（单独任务）

1. 新项目不再显示 screen-reference.v1；保留旧快照只读解析。
2. grep 确认无引用后移除废弃导出脚本、遗留 generator IPC、不可达的 miniprogram 预览回退。
3. 生图、Prompt Studio、海报素材转为可选模块或 demo。
4. 按项目/候选/预览/Agent 拆分 App.jsx 与 sessionMachine.mjs，每次拆分保持行为测试。
5. 单独处理 catalog 漂移、MIRROR CRLF 摘要、composer:verify PATH_ESCAPE；禁止通过 catalog:write 或 mirror:sync 掩盖既有基线失败。

验收：无生产入口引用；旧项目可打开；P0–P3 行为不回归。

## 6. 前端模型交接边界

### 可以负责

- React 页面与组件：Composer、候选卡、版本时间线、截图对比、右栏对话。
- Hooks：useFrontendReconstruct、useProjectVersions、useScreenshotPair。
- 样式、无障碍名称、稳定 automation id。
- 薄 facade 适配层，只调用 preload 暴露的方法。

### 不负责

- 不改 frontend-reconstruct.v1 契约字段和后端状态含义。
- 不执行 Composer/微信 CLI/文件系统/任意命令。
- 不读取 userData 路径或 miniprogram/。
- 不在 React 重建候选状态机、undo 栈或图片识别链。
- 不把 partial/BLOCKED/NOT_RUN 显示成成功。

### 前端交付

提供组件/hook 接口说明；关键控件有可读名称、必要 aria-label 和稳定 id；覆盖 loading、empty、failed、blocked、not-run、partial、ready 状态；提供采用、撤销、redo 和版本切换的行为验证；按仓库约定执行 npm run agent:smoke，新增关键控件补 agent:verify 断言。

## 7. 阶段门禁与完成定义

按改动运行必要门禁，并如实记录基线与环境阻塞：

~~~powershell
npm test
npm run build
npm run test:desktop
npm run check:packaging
npm run frontend:capabilities:check
npm run frontend:verify -- --attempt <attemptDir>
npm run frontend:verify -- --attempt <attemptDir> --runtime
npm run agent:smoke
npm run mini:check
npm run mirror:check
~~~

安装版 P0 证据包括包版本、CLI 解析结果、固定验证脚本执行结果、页面截图数、关键交互结果。工具未安装或不可运行写 BLOCKED，不用静态 dry-run 代替。

MVP 完成必须满足：单一图文入口；请求基于当前项目版本；受控候选经过 dry-run；微信状态涵盖页面和关键交互；真实 before/after 同路由同尺寸或明确缺失；采用、undo、redo、重开、导出共享一个版本历史；前端只依赖 facade。满足后再清理旧代码或扩展非核心能力。
