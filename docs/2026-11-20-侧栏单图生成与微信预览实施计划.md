# 侧栏单图生成与微信预览实施计划

## 用户目标与骨架定义

店主在任意已打开的项目阶段，发送一张界面样例和一段描述。桌面应用填入有依据的店铺资料，生成与样例相匹配的新页面骨架，构建和验证项目私有工程，最后由用户在微信中预览验收。

“新骨架”要通过结构变化来验收：生成出来的组件和分区树应表达样例里的布局，换一张布局明显不同的样例后，生成的结构也应相应改变。只更换颜色、文案或卡片大小不算生成了新骨架。侧栏需要把生成结果、近似项及不支持项说清楚，不能把模型文字回复当成实现结果。

当前 `frontend-reconstruct.v1` 已能从参考图构造受限 DSL，并生成首页或菜单页的 WXML/WXSS/JSON。它支持重排当前 Base 和组件目录中的组件、slot、容器、文案和受限按钮。组件、数据路径、事件动作、页面 ID 和样式值均由机器契约及能力目录约束。[候选契约](../contracts/frontend-reconstruct.v1.json) · [渲染器](../desktop/frontend-reconstruct/render.cjs) · [字段与动作目录](../src/domain/appCapabilities.mjs)

因此当前链路可以交付**基于现有能力的新页面骨架组合**。它不能凭一张图创建一个目录中不存在的新组件、新页面、新数据模型或业务动作，也不能让模型直接生成任意小程序源码。若目标样例要求这些新增能力，必须先将它们设计成版本化的页面/组件/动作能力，扩展 FrontendPack 契约、事实目录、生成器和微信测试；侧栏再使用扩展后的能力构建候选。能力缺口应明确显示，不能降级冒充完整实现。

## 首版范围与扩展边界

首版用现有 FrontendPack 生成项目私有的首页或菜单页新骨架组合。未提到的店铺资料沿用项目现值，可选项留空。只有会影响本轮结果的歧义或缺项才打断流程。至少用两张布局明显不同的样例验收 DSL 结构变化。如果样例超出当前能力边界，先记录能力缺口并决定是否扩展契约，再承诺实现。

用户看到的「已打开微信预览」、验证报告中的运行时结果和用户对视觉效果的判断各有独立含义。

## 骨架继续制作入口

候选通过现有 schema、白名单 renderer 和 Composer 静态门禁后，在候选结果卡显示「按这个骨架继续制作」。同处提供「修改要求并重新生成」，让用户能返回调整当前描述后生成新 attempt。

点击「按这个骨架继续制作」才执行现有 `frontend.adopt` 确认动作，将当前 candidate ID、版本、digest、run 和 attempt 绑定到项目快照。之后项目 Plan、静态检查和正式 Composer 导出都以该 FrontendPack overlay 为准。将工作流继续到后续项目制作阶段，不在此动作中打开预览。

如果运行时验证为 `PASS`，按正常采用路径继续。如果为 `BLOCKED`、`NOT_RUN` 或其他部分状态，保留既有单独确认机制并如实记录。采用前生成失败、候选超出能力或摘要不匹配时，不显示可继续按钮。改要求重新生成时使用新的 attempt，不覆盖已采用版本。

最终微信小程序预览仍用于整项工程完成后的人工验收。工作台现有 `MiniProgramPreview` 不增加候选预览模式，也不作为自定义骨架的验收依据。

## 骨架能力验收门槛

在侧栏与微信预览编排工作之前，先用两张布局差异明显的归档样例配上各自明确描述，走当前的真实分析、生成和白名单校验流程。

- 比较两次生成的节点树、组件序列、slot 顺序、容器层级和关键页面属性。至少有与样例布局差异相对应的结构变化，而非只有主题或文案变化。
- 确认输出工程包含这些结构变化，微信实际渲染出的布局与节点树一致。
- 对样例要求里属于已支持能力的部分做逐项覆盖核对。对于未支持组件、页面和交互列出具体能力缺口，并确认不会被静默忽略。

如果当前能力不能通过上述门槛，先实施“骨架能力扩展”，范围按样例中发现的具体缺口限定。扩展应增加有事实定义的组件、页面或动作，由受控 DSL 引用，再补白名单校验、确定性 renderer、Composer 集成和运行时测试。契约存在不兼容变化时升级版本并生成两侧代码。不得通过放宽为任意源码生成绕开此门槛。

## 固定验收场景

从一个已打开、当前停在「功能选择」的项目开始，附上一张首页参考图，发送「店名叫山禾咖啡，支持到店自取，生椰拿铁 18 元。首页按图把店名放在上方，自取入口放在店名下方」。准备一张结构与这段话一致、允许归档的参考图。验收时同时核对以下结果。

- 桌面变更卡能看到店名、取餐方式和菜品价格。工作区自动定位到候选面板，侧栏持续显示同一轮任务的进度。
- 本轮私有候选包含首页布局变更，用户能在微信首页看到店名和自取入口的相对位置。菜单显示生椰拿铁 18 元，加入购物车后商品和金额正确。
- 配套的第二张明显不同布局样例生成不同的页面结构。两次运行均显示实际覆盖与能力缺口，微信渲染与各自生成的节点树一致。
- 候选通过后点击「按这个骨架继续制作」，后续工程生成和导出使用该候选。项目制作完成后，沿用现有微信预览入口最终验收。重开项目可识别已采用版本，撤销采用可回到上一版。

## 里程碑一　验证参考图能生成不同的页面骨架

1. 准备两张布局结构明显不同、来源及使用权限可记录的首页或菜单页样例，并为每张图写清页面目标、必须保留的店铺功能和结构要求。
2. 走现有分析、覆盖评估、DSL proposal、白名单 renderer 和 Composer dry-run。保留脱敏后的结构摘要、能力报告和工程摘要，逐项比较节点树、组件/slot 编排和容器结构是否响应不同样例。
3. 对照微信实际页面确认结构已落入导出工程。如果第一张简单样例能通过、第二张因缺少必要组件/页面/动作而无法通过，则当前契约不满足目标，按“骨架能力验收门槛”中的缺口先扩能力，再继续侧栏自动化。

**交付检查**　至少两种不同结构在同一组既有能力内生成可区分的页面骨架，并能从输出工程和微信页面独立复核。能力外要求必须显示为缺口或拒绝原因。未达到前，不把后续流程描述为“按样例搭建新前端”已完成。

## 里程碑二　先用固定输入打通真实微信预览

1. 从已写回的项目状态构造 Composer Plan，明确采用本轮草稿中的店名和菜品。接入现有候选构建与 dry-run，使侧栏任务显式传入这份 Plan。现有验证默认读取 `order-warm-home` 示例，现有预览会另行导出，两处都要接到本次构建结果。[项目 Plan](../src/composition/planFromSession.mjs) · [候选 dry-run](../desktop/frontend-reconstruct/dry-run.cjs) · [预览组合入口](../src/App.jsx)
2. 给开发预览提供独立的预览门店，冻结本轮店铺资料和菜单版本。先核实现有开发后端的门店分配与身份机制。需要补齐分配时，由后端绑定预览目标和所有者。复用现有带门店权限校验的资料导入与幂等能力，只向预览门店写入。Composer 将相应的 `storeId` 写入工程，用小程序实际调用的门店和菜单接口回读店名、商品和价格。两个项目或同一项目两个仍可打开的版本应能分别读到各自的数据。[资料导入](../server/src/imports/imports.controller.ts) · [Composer 配置生成](../scripts/composer/emit.cjs) · [小程序门店与菜单取数](../templates/base/ordering-base/1.0.0/src/services/store.js)
3. 为本次 attempt 绑定私有候选、Plan 摘要、预览门店数据版本和 Composer 工程。提前完成开发 AppID 配置及工程身份检查，再做微信运行时验证。最后打开这份已验证工程。数据或布局变化后重建受影响产物，旧证据归属原版本。[验证入口](../scripts/frontend-verify.cjs) · [微信预览通道](../desktop/preview-channel.cjs)

**交付检查**　先用固定合法草稿跑一次真实微信，再用不同店名和价格跑第二次。重新打开第一份工程仍看到第一组资料，两个工程都能打开菜单并加购。留存工程与 Plan 摘要、数据版本、微信截图和交互结果。

## 里程碑三　让一次发送同时填资料和生成候选

1. 在侧栏统一处理一张图的用途。显式选「参考界面」或清楚写出「首页按图做」即可发起候选任务。自动判断为参考图且生成意图明确时进入同一入口。用途或生成意图含糊时在原消息追问，并在本次会话保留附件供继续使用。菜单识别继续走 `agent-turn.v2`，以 `vision.analyzed=true` 作为回写门槛。
2. 发送前展示图片、用途和实际接收方。明确的「发送并生成」同时表达本图重构意图并生成现有 consent，主进程继续核对图片摘要、接收方和有效期。意图需追问时，将生成确认合并到用户的回答。已明确用途的参考图由候选服务接收，资料提案可单独使用同一条文字。[发图确认](../src/domain/screenConsent.mjs) · [候选主进程入口](../desktop/frontend-reconstruct-ipc.cjs)
3. 保留 `app-assistant.v1` 提案和桌面 reducer 的原子写回。写回成功后读取新的项目版本，再交给候选任务。清空字段、删菜等高风险动作仍进入待确认区。导航复用合法阶段，初版跳到已承载候选面板的「门店资料」，在面板挂载后定位。导航本身只改变用户看到的阶段。[侧栏分流与阶段视图](../src/App.jsx) · [动作执行器](../src/services/appAssistant/actionExecutor.js)

**交付检查**　覆盖显式参考图、自动识别、用途含糊、菜单照四种输入。固定验收消息同时产生资料变更卡和一个候选任务。更新原有“侧栏只投递”的断言，分别覆盖用户明确发起生成和模型仅提议生成。项目切换后，迟到的响应不会改写当前项目。

## 里程碑四　自动运行候选构建和验证

1. 从 React 点击处理函数中提取可复用的任务调用。手动面板与侧栏共用候选服务和状态机。分析得到 `planned` 后直接调用构建，构建内已有静态验证，通过后进入微信验证。侧栏只消费实际阶段、工具标签和结果。[候选服务](../src/services/frontendReconstruct/frontendReconstructService.js) · [状态机](../src/domain/frontendReconstruct.mjs)
2. 用项目、请求、run、revision 和 attempt 标识每次操作。任务持有本轮输入，在清空输入框、切换阶段和重复点击后仍只处理一次。取消、切换项目或修改相关资料后校验结果归属。仅重试失败步骤，已应用的字段批次保留撤销记录。
3. 分析需要补充时在侧栏续答，缺必需能力时列明原因并结束本轮。静态失败只对可定位到 DSL 的问题修复，最多两轮，每次保留独立 attempt。桌面主进程目前未注入真实 `repairTransport`。先交付如实报告失败的链路，再接通修复并用可修复样例验证。微信环境故障从验证步骤恢复。[修复入口](../desktop/frontend-reconstruct-ipc.cjs) · [主进程注册](../desktop/main.cjs)

**交付检查**　正常样例自动走到可预览，过程中无需点击「识别」「构建」「验证」。重复发送、取消和过期回包均有回归测试。修复通道可用时能复核每次 attempt 的问题和结论。不可用时直接显示具体失败原因。

## 里程碑五　按自定义骨架继续制作

1. 候选通过静态构建后，在候选结果卡显示「按这个骨架继续制作」和「修改要求并重新生成」。不增加桌面候选预览或自动打开微信的步骤。
2. 主按钮按现有确认边界采用候选。执行前复核当前项目、candidate ID、digest、run 和 attempt。成功后将同一 overlay 持久化到项目，进入项目后续制作阶段。后续 Composer Plan、校验和导出都使用此版本。保留上一版并支持撤销。[采用记录](../desktop/frontend-reconstruct/adoption.cjs) · [桌面采用桥接](../src/services/frontendReconstruct/adoptionBridge.js)
3. 运行时验证为 `PASS` 时按正常路径继续。若为 `FAIL`，展示失败项并停留在当前候选。如果是 `BLOCKED` 或 `NOT_RUN`，提供重试验证和原有部分采用确认。环境问题不能伪报通过。重复点击只产生一份采用记录。

**交付检查**　确认主按钮只采用所示候选并继续项目流程，不自动打开预览。重开项目后可复核同一 overlay，撤销可以恢复上一版本。后续导出的页面文件摘要与已采用 candidate 对应。失败、部分验证、重复点击和重建 attempt 都有明确可恢复状态。

## 里程碑六　从真实侧栏发起交付验收

| 场景 | 验收证据 |
| --- | --- |
| 两张不同结构的清晰参考图 | 用真实模型、Electron 和微信开发者工具分别运行。比较生成树、能力覆盖、工程摘要及微信截图，证明结构变化由参考图驱动且进入运行工程。 |
| 清晰参考图和完整描述 | 用真实模型、Electron 和微信开发者工具跑固定样例。记录侧栏操作次数、字段变更、候选标识、Plan 与工程摘要、真实首页和菜单截图、加购及关键下单回归结果。 |
| 模糊图或要求超出首页、菜单页能力 | 模糊图给出具体追问，可以在侧栏继续。明确缺少必需能力时显示拒绝原因。 |
| 执行中切项目、改资料、取消、双击 | 原项目与当前项目资料分别正确，旧版本结果不会覆盖新版，同一请求只应用一次。 |
| 微信环境异常后恢复 | 显示实际故障状态，恢复后验证同一候选。验收记录引用真实微信报告。 |
| 按骨架继续、重开、撤销 | 采用的是结果卡上指定的候选，后续 Composer 输出与其摘要对应，重开可复核，撤销能恢复上一版。 |

实现阶段按涉及的入口跑 `npm test`、`npm run build` 和相应服务端测试。桌面改动运行 `npm run agent:smoke`、`npm run app:assistant:smoke`，用 UIA 断言侧栏主按钮、追问和失败状态。候选独立复核沿用 `npm run frontend:verify -- --attempt <attemptDir> --runtime`。字段目录或机器契约发生修改时再生成对应快照并检查漂移。验收留存可复核的测试图、摘要、运行时截图与报告，侧栏过程卡仅显示允许展示的执行信息。

实施顺序为一 → 二 → 三 → 四 → 五 → 六。第一个成果是证明不同样例能驱动不同页面骨架；如果当前白名单能力覆盖不足，先扩展具体能力。接着打通微信工程和本轮数据，然后让侧栏自动生成候选，并在结果卡提供按骨架继续制作的确认入口。整项工程完成后沿用现有微信小程序预览作人工验收，不新增候选桌面预览。
