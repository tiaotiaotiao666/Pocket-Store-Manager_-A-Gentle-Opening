# 后端实现方案与套餐

> 本文统一后端范围、阶段顺序和套餐边界。API 字段以 `docs/api.md` 为准，订单规则以 `docs/order-state.md` 为准。
> 模板库的详细架构见 `docs/模板库与组合生成规划.md`；本文只规定它与 B0–B5 的先后关系。
> 当前状态：B0 已完成并验收，B1 业务模块尚未开始；NestJS AgentModule 与 DeepSeek 资料收集已另行完成，不属于 B1 点餐闭环。

## 1. 产品路线

项目分为四条有依赖关系、可独立验收的工作线：

1. **桌面生成器**：本机收集门店资料、选择已验证模板和风格、预览并导出独立微信原生小程序工程。
2. **点餐业务后端与小程序**：使用 `/api/v1` 为门店目录、顾客订单和店主工作台提供在线能力，是首个业务交付主线。
3. **模板库与确定性组合生成**：在 B2 验证 Base 和组件，之后通过 Manifest、CompositionPlan 和 Composer 扩展模板，不让 Agent 直接生成业务源码。
4. **生成器云端协作能力**：项目/会话、注册表、组合任务、生图和部署任务，独立排期，不阻塞点餐闭环。

首期业务范围为单套服务、多门店按 `storeId` 隔离，跑通“运维预置门店和店主 → 顾客扫码浏览 → 创建订单 → 演示模拟付款 → 店主处理订单”。真实微信支付、退款、配送、公开店主注册和自动审核发布不在首期范围。

## 2. 技术与分层约束

- Node.js 22+、NestJS 11、TypeScript；API 使用 `/api/v1`。
- MySQL 8 + Prisma 6 管理持久化和迁移；生产映射 RDS。
- Redis 用于目录缓存及按需的会话/任务加速；订单、状态历史和幂等记录以 MySQL 为准，生产映射 DCS。
- 金额只用整数分，订单保存名称和单价快照，总价由服务端计算。
- 服务端用微信 `code` 换 OpenID；演示登录由显式非生产开关启用。OWNER/STAFF 只从数据库 membership 读取。
- Controller 负责 HTTP/DTO，Service 实现用例和权限，Prisma 负责存取；订单跨表写入在事务内完成。
- 密钥只存在服务端环境或密钥管理系统，不进入前端、导出工程或日志。
- 小程序坚持微信原生；页面组合、组件展示与发事件、服务层请求，组件不直接触网。
- 模板组合必须确定性、可复现、可测试；Agent 只输出受约束的组合规格。

## 3. 分阶段实施

### B0：契约与演示数据冻结——已完成

已交付 API/订单/数据模型契约、Prisma schema、初始迁移、可重复种子、MySQL/Redis 基础设施和本地复现文档。Redis 真实链路已验收。

### B1：业务后端最小闭环——当前后端主线

- 实现 `common`、`auth`、`stores`、`catalog`、`orders`、`merchant`。
- 按契约实现登录/me、公开门店和目录、创建/查询/取消订单、演示付款、店主订单与商品上下架。
- 下单事务内重新校验门店、桌号和可售商品，以数据库价格计价，保存快照、初始日志和幂等记录。
- 状态更新校验转换矩阵，使用条件更新并在同一事务写日志。
- 商品上下架递增目录版本，提交后失效 Redis。
- 验收：S1–S12、权限/租户、重复下单和停售快照测试全部通过。

**B1 不加入模板库、Composer、Agent 组合规划或云端项目持久化。** 唯一执行入口为 `docs/handoff/后端B1交接.md`。

### B2：小程序接入与 Base 验证

- 只改造 `miniprogram/`，建立统一 API service，接扫码场景、顾客菜单/结算/订单、模拟付款和店主订单台。
- 创建订单时持久化并复用 `Idempotency-Key`，客户端不传单价或总价。
- 按 `docs/component-contract.md` 落地核心 UI Block，验证“页面组合、组件纯展示、服务层请求”。
- 形成 Base Template 候选：无可选营销组件也能完成核心闭环；删除可选组件不影响编译和核心链路。
- 此阶段保持 `templates/mini-program/` 静态模板不动，不同时发展两套组件源。
- 验收：微信开发者工具完成端到端演示，模拟付款明确标注，组件可删除性检查通过。

### B2 后、B3 前：本地 Composer 独立验收

- 冻结 Manifest、CompositionPlan、插槽和 Lock 契约。
- 从 B2 参考工程提炼唯一 Base 和组件源，使用固定 Plan 确定性生成少量 Recipe。
- 将现有 Electron 导出从“复制静态模板”升级为 Composer 调用，保留安全的本地文件输出能力。
- 桌面预览与导出共用组合规格；最终仍以微信开发者工具验收真实产物。
- 验收：固定 Plan 可生成完整工程，相同 Lock 可复现，微信编译和核心回归通过，失败无半成品。

### B3：生成器接业务后端并统一模板源

- 增加受控门店配置导入/初始化，写入门店、分类、商品和桌号；重复导入防重，避免覆盖运营数据。
- 导出工程只写公开 API Base URL、`storeId` 和公开配置，不写任何秘密。
- `store.generated.json` 与 CompositionPlan 分别承担门店数据和组合规格，版本映射不兼容时明确拒绝。
- 统一参考工程与导出模板的组件事实来源，退出双份手工维护。
- 验收：重复导入行为确定、变更可审计、生成工程指向正确门店。

### B4：云端发布与运维

- 在可复现环境验证后接 RDS、DCS、ECS/容器、HTTPS/API Gateway、日志和备份。
- 模型服务单独验证能力、区域、鉴权和响应格式，未经真实探测不得显示“已接入”。
- 配置 TLS、CORS、微信合法域名、隐私说明、限流、监控和恢复演练。
- 验收：备份恢复、健康探测、敏感信息扫描、部署回滚和端到端证据齐全。

### B5：桌面生成器与模板平台云端能力

- 项目/会话、目录、提示词、生图、部署和云端导出按 `docs/后端待实现接口清单.md` 独立实施。
- 本地 Composer 验证后，再增加 `TemplateRegistryModule` 和 `CompositionModule`；不得提前维护文件与数据库两套注册表事实。
- Agent 组合规划使用独立契约，复用 Provider 隔离与服务端独立校验，不改变 `agent-turn.v1` 的资料收集语义。
- 长任务持久化，项目与图片按 owner 隔离；组件源码只来自可信发布包。
- 验收：刷新恢复、任务可重试、用户隔离、组合可复现、模型配置状态准确。

## 4. 套餐边界

| 套餐 | 交付范围 | 不包含 |
| --- | --- | --- |
| A. 后端核心包 | B0 + B1，业务 API、数据层和 S1–S12 | 小程序页面、生成器导入、模板组合 |
| B. 可演示闭环包 | A + B2，顾客端和店主端真实 API 演示 | 真实支付、生产 SLA、云端会话、Composer |
| C. 门店配置联通包 | B + B3；B3 前须完成本地 Composer 独立验收 | 自助注册、在线改价、开放式代码生成 |
| D. 云部署加固包 | C + B4，目标云部署和运维验证 | 微信支付、外送、自动审核发布 |
| E. 生成器云端协作包 | B5，项目/会话、模型任务及模板平台云端化 | 点餐闭环强依赖、模型自由生成源码 |

模板库属于横向增量路线：T1 与 B2 同体验证，T2 是 B3 前置验收，T3 随 B3 统一和扩展，T4 在 B5 云端化。详细 T0–T4 见模板库规划，工作量单独评估，不悄然扩张已批准的 B 套餐。

## 5. 已确认默认值

1. 首个完整里程碑为 B 套餐；当前先完成 B1，再进入 B2。
2. 首期为单服务多门店，按 `storeId` 隔离，不是每店独立部署后端。
3. 演示登录和支付只允许非生产显式开关；生产必须关闭。
4. 菜单由种子/受控导入维护，首期不提供公开新增、改价和删除 API。
5. 当前真实开店资料 Provider 为 DeepSeek；ModelArts/盘古尚未接入。
6. Agent 不负责开放式代码生成。未来模板组合也只选择注册表中的版本化资产，由 Composer 生成。
7. 生成器部署最多生成工程并上传演示环境，不代替店主向微信平台发布。
