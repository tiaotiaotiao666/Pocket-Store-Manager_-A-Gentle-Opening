## 3. 实施顺序

严格按 `common → auth → stores/catalog → orders → merchant` 串行实施，每个模块完成后先测试再进入下一步。

### 3.1 common

建议职责：

- 统一错误体 `{code,message,requestId,details?}`，禁止堆栈、SQL、OpenID 和秘密外泄。
- requestId 同时写响应头 `X-Request-Id`。
- DTO 白名单校验和转换。
- Auth Guard：Bearer opaque token 的 SHA-256 查询 `sessions`，校验过期。
- StoreMember Guard：从 `store_members` 读取 OWNER/STAFF，处理跨店和资源不存在。
- 当前用户装饰器、稳定 ID 和业务错误构造。

### 3.2 auth

实现：

- `POST /auth/wechat/login`
- `GET /auth/me`

规则：真实 code 只由服务端换 OpenID；demoOpenId 仅在非生产且 `ALLOW_DEMO_LOGIN=true` 时接受。首次登录可创建用户，但不创建成员或授权。Token 使用安全随机 opaque 值，数据库只存哈希，默认 7 天过期；memberships 只读数据库。

### 3.3 stores / catalog

实现：

- `GET /stores/:storeId`
- `GET /stores/:storeId/catalog`

公开目录只返回 `available=true`。缓存键 `catalog:{storeId}`，返回 `stores.catalogVersion` 和 `updatedAt`；金额只用 `priceCents`。

### 3.4 orders

实现：

- `POST /orders`
- `POST /orders/:id/demo-payment`
- `POST /orders/:id/cancel`
- `GET /orders`
- `GET /orders/:id`

创建订单必须带 8–128 位可见 ASCII 的 `Idempotency-Key`。事务内校验门店、履约和桌号归属，过滤不可售商品，合并重复 productId，按数据库价格计算，写订单、快照、首条日志和幂等记录。

幂等键按用户+门店+Key 唯一；指纹一致返回原订单，不一致返回 `409 IDEMPOTENCY_CONFLICT`。模拟付款只允许本人 PENDING_PAYMENT，生产或关闭开关时拒绝；取消和查询权限严格按契约。

### 3.5 merchant

实现：

- `GET /merchant/stores/:storeId/orders`
- `PATCH /merchant/orders/:id/status`
- `PATCH /merchant/products/:id/availability`
- `GET /merchant/stores/:storeId/products`

所有接口要求该店 OWNER/STAFF。状态推进先校验矩阵，再用 expectedStatus 条件更新，同事务写日志；受影响 0 行返回 `409 STATUS_CONFLICT`。待付款订单不可由店主处理。上下架在事务内递增 catalogVersion，提交后删除目录缓存。
