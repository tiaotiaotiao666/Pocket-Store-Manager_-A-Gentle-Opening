## 1. 项目要解决什么

“智能开店 / 口袋店长·轻启”包含一个 Windows 桌面生成器和其生成的微信原生门店小程序。近期业务目标是完成餐饮扫码点餐答辩 MVP，后续目标是通过可验证的模板资产库，让 Agent 按店主需求组合不同小程序模板。

当前首要交付不是模板数量，而是：

```text
运维预置门店与店主
→ 顾客扫码浏览菜单
→ 创建订单
→ 演示模拟付款
→ 店主接单、制作、可取餐、完成
```

真实微信支付、退款、外送、公开店主注册、客户端授权和自动审核发布不在 MVP 范围。

## 5. 关键架构边界

### 桌面端

`App.jsx` 是组合根；组件不直接请求 API、不读取全局业务状态。服务层处理外部能力，reducer 和 domain 保持纯函数。桌面 React 小程序预览只是实时效果预览，不能替代微信运行时验收。

### 小程序

坚持微信原生，不使用 Taro/uni-app。页面组合组件并调用服务层；组件只接收 properties、只发事件，禁止 API、`globalData` 业务状态和固定路由。详见 `docs/component-contract.md`。

### 后端

NestJS 模块化，MySQL 负责业务事实，Redis 负责缓存和按需加速。API 使用 `/api/v1`，金额只用整数分并由服务端计算，门店资源按 `storeId` 隔离，角色只从数据库 membership 获取。

### Agent 与模板

当前 `agent-turn.v1` 只负责资料收集。未来 Agent 只输出白名单 CompositionPlan，不能生成任意业务源码；确定性 Composer 从可信版本化资产生成工程，并用 Lock 保证可复现。

## 6. 当前执行顺序

```text
1. B1：common → auth → stores/catalog → orders → merchant → S1–S12
2. B2：miniprogram 接真实 API，同时验证 Base 与核心组件
3. B2 后：固定 Plan 打通本地 Composer，接真实 Electron 导出
4. B3：统一模板源，受控联通门店配置
5. 持续扩展海报轮播、营销区、广告位、优惠券等资产
6. B5：云端项目/会话、注册表、组合任务和独立 Agent 组合规划
```

B1 执行入口：`docs/handoff/后端B1交接.md`。当前工作区及前端未提交改动：`docs/handoff/当前工作区交接.md`。

## 7. 当前主要风险

- 桌面预览和导出 WXML 尚未共享组合规格，可能漂移。
- `miniprogram/` 与静态导出模板尚未统一，不得同时各建组件体系。
- 当前导出仍是复制和定点覆盖，不是 Composer。
- 导出脚本运行时引用 `src/domain/catalog.mjs`，安装包 files 未包含 `src/`，需真实安装包验证。
- `test:desktop` 指向尚不存在的测试文件。
- Windows 安装包上次受 Electron 下载超时阻塞，未完成最终安装验收。
- Agent 的 Authorization 目前只检查 Bearer 形式，不是真实店主身份认证。
- ModelArts/盘古未接入；不得将 OpenAI 兼容适配或 DeepSeek 资料收集描述为华为云模型接通。
