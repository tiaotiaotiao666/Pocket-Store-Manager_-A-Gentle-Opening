# 小程序模板库与组合生成规划

> 状态：**本地 Composer 与首批资产已落地；云端注册表/组合模块仍规划**。
> 2026-11-03 实测：`base 1 / ui-block 3 / feature-pack 1 / recipe 3（direct 2）`，三份 Recipe 已生成工程并通过微信编译，
> `order-classic`、`order-poster` 已晋升正式模板。证据见 `docs/evidence/m7/`。
> 本文是模板库、组件注册表、CompositionPlan 和 Composer 的唯一规划入口；第 8 节的云端能力仍未实现，不得描述为已存在。
> 实施顺序服从 `docs/后端实现方案与套餐.md`：B1 范围不被模板库扩张，B2 先验证基础版，再建设本地 Composer，最后接 Agent 和云端能力。

## 1. 目标与核心决策

目标是在微信原生小程序技术栈下，用少量稳定基础代码和持续增加的已验证组件，生成多种门店模板，而不是为每套模板复制一份完整工程。

采用以下核心决策：

```text
版本化 Base Template
+ 版本化 UI Block / Feature Pack / Recipe
+ 机器可读 Manifest
+ 声明式 CompositionPlan
+ 确定性 Composer
+ 自动化兼容性验证
+ Agent 只生成受约束的组合规格
```

Agent 不直接生成或修改 WXML、JS、WXSS，不自由引入依赖，不直接写生成目录。所有源码只能来自仓库内经过审核和测试的版本化模板资产。

## 2. 非目标

- 不做开放式 AI 业务代码生成。
- 不做运行时按模型输出动态加载任意组件路径。
- 不引入 Taro、uni-app 等跨端框架。
- 不让组件直接请求 API、读取全局业务状态或固定业务路由。
- 不把每一种 Agent 组合都自动发布成正式模板。
- 不用桌面 React 预览通过替代微信开发者工具验收。
- 不在后端能力未实现时，把营销 UI 宣称为可上线的真实业务能力。

## 3. 四层模板资产

### 3.1 Base Template：基础模板

基础模板只包含所有点餐模板共同需要的稳定能力：

- 微信原生工程骨架、页面注册和导航约定；
- 全局主题 Token、配置加载和公开运行配置；
- 服务层请求、Token、错误归一化、超时和重新登录；
- 加载、空数据、异常等通用状态；
- 首页、菜单、购物与结算、订单、我的，以及当前 B2 演示要求的店主订单台；
- 门店、商品、订单的在线数据接入；
- 稳定的页面插槽协议。

广告、优惠券、海报轮播和行业化营销页面不得进入首版 Base。

“兼容性最强”必须通过可执行标准证明：明确最低微信基础库版本、无可选组件时独立运行、删除任一可选组件不影响核心链路、经过微信开发者工具和代表性运行环境验证。

### 3.2 UI Block：纯展示组件

例如 `hero-carousel`、`poster-banner`、`coupon-card`、`product-card`、`store-header`、`state-view`。

UI Block 只通过 `properties` 接收数据，通过 `triggerEvent` 发出用户意图，遵守 `docs/component-contract.md`。组件不得自行决定业务路由或请求广告、优惠券等接口。

### 3.3 Feature Pack：业务能力包

复杂业务不是单个展示组件。Feature Pack 可以包含：

```text
feature-pack/
├─ components/       纯展示组件
├─ pages/            页面组合、状态和导航
├─ services/         服务层请求
├─ manifest.json     依赖、插槽、后端能力和兼容性声明
└─ tests/            组件与组合测试
```

API 只允许出现在页面或服务层。优惠券等能力在后端未完成时可以具有 `preview-only` UI，但不得标记为可正式发布。

### 3.4 Recipe：模板配方

Recipe 是一份经过验证的组合配方，而不是一份复制后独立维护的小程序源码。它包含：

- Base 和注册表版本；
- Feature Pack 列表；
- 页面布局和插槽组件；
- 默认主题 Token；
- 预览示例数据；
- 后端 API 契约版本；
- 验证记录和发布状态。

必须区分：

| 概念 | 含义 |
| --- | --- |
| 生成实例 | 为某一家门店生成的小程序工程 |
| 候选 Recipe | Agent 或开发者新组合、尚未完整验证的方案 |
| 正式 Recipe | 编译、测试和发布审核通过，可供用户选择的模板 |

## 4. 唯一事实来源与目录演进

当前 `miniprogram/` 是 B2 在线点餐参考工程，`templates/mini-program/` 是静态导出模板。两者不得分别发展一套组件体系。

过渡规则：

1. B2 只在 `miniprogram/` 验证 Base、服务层和核心组件，保持静态导出模板不动。
2. B2 完成后，从通过验证的参考工程提炼唯一 Base 和组件源。
3. 本地 Composer 打通后，导出工程由同一组合规格生成；旧静态复制链路逐步退出，不形成第三份事实来源。
4. 桌面预览、Composer 和测试共用 CompositionPlan、主题 Token 与示例数据。

长期目标目录仅为规划，实施时按任务清单落地：

```text
templates/
├─ base/               唯一基础模板源
├─ components/         版本化 UI Block
├─ features/           版本化 Feature Pack
├─ recipes/            已验证组合配方
└─ registry/           Manifest、Schema、注册表版本
miniprogram/           参考与验证工程，不另养一套组件实现
scripts/composer/      确定性组合器
```

## 5. Manifest 契约

每个 UI Block、Feature Pack、Base 和 Recipe 都必须有机器可读 Manifest。字段至少包括：

| 类别 | 必填信息 |
| --- | --- |
| 身份 | `id`、`version`、`kind`、`registryVersion` |
| 入口 | 可信包内相对入口，禁止绝对路径和路径逃逸 |
| 兼容性 | Base 版本范围、最低微信基础库、后端 API 契约版本 |
| 组合 | 允许的插槽、依赖、冲突、插槽容量、所需页面 |
| 组件通信 | `properties`、`events` 的 Schema 和默认值 |
| 视觉 | 使用的主题 Token、资源约束、预览示例数据 |
| 发布 | `preview-only` / `online-ready`、已验证 Recipe、发布状态 |
| 验证 | 测试入口、微信编译要求、已知限制 |

首阶段 Manifest 和代码共同存放在 Git，评审和版本保持一致。不得同时维护文件注册表和数据库注册表两套事实。

## 6. CompositionPlan 与 Lock

CompositionPlan 是 Agent、桌面预览、Composer 和测试共用的声明式输入。示例仅表示目标契约，尚未实现：

```json
{
  "schemaVersion": "composition.v1",
  "baseTemplate": { "id": "ordering-base", "version": "1.0.0" },
  "registryVersion": "2026.11.0",
  "features": [
    { "id": "catalog", "version": "1.0.0" },
    { "id": "ordering", "version": "1.0.0" },
    { "id": "poster-carousel", "version": "1.0.0" }
  ],
  "pages": [
    {
      "id": "home",
      "layout": "home.standard",
      "slots": {
        "hero": [
          {
            "component": "hero-carousel",
            "version": "1.0.0",
            "props": { "autoplay": true, "interval": 4000 }
          }
        ]
      }
    }
  ],
  "themeTokens": {
    "primaryColor": "#7357D9",
    "pageBackground": "#FAFAFC"
  },
  "apiBinding": { "contractVersion": "storefront.v1" }
}
```

CompositionPlan 不得包含源码、AppSecret、数据库连接、模型密钥、用户 Token、任意文件路径或脚本。

Composer 解析后必须生成 `composition.lock.json`，记录 Base、注册表、组件、依赖和 Composer 的精确版本及源版本/产物校验信息。相同 Lock 应生成可复现结果，不允许每次静默选择“最新组件”。

门店业务数据与 CompositionPlan 分离。导出工程只写公开 API Base URL、`storeId` 和非敏感公开配置。

## 7. 确定性 Composer

Composer 是模板平台的核心，职责依次为：

1. JSON Schema 和版本校验；
2. 注册表白名单、可信入口和兼容范围校验；
3. 依赖、冲突、循环、插槽和容量解析；
4. 页面、路由、tabBar、所需服务与后端能力完整性检查；
5. 固定精确版本并生成 Lock；
6. 从可信资产生成静态 WXML、页面 JSON、`usingComponents`、`app.json`、主题 WXSS 和公开运行配置；
7. 运行组件边界、敏感信息和路径安全检查；
8. 执行组合测试和微信开发者工具编译；
9. 原子输出完整工程，失败清理本次半成品并生成可读报告。

微信原生小程序的页面注册和组件引用在构建期确定。运行时只处理业务数据变化，不执行模型输出的动态代码。

现有 `scripts/generate-mini-program.cjs` 的目录创建、失败清理、图标写入等能力可以复用；“整目录复制 + 字符串替换”不等同于 Composer。

## 8. Agent 与后端边界

沿用 `agent-turn.v1` 的原则：模型输出只是候选，服务端/本地确定性逻辑决定最终事实。

推荐链路：

```text
用户需求
→ 按 Base、功能、兼容性和发布状态筛选 Manifest 摘要
→ Agent 返回 CompositionPlan 候选
→ 独立 Schema 与能力校验
→ 用户确认组合
→ Composer 生成与测试
→ 通过后导出；候选 Recipe 经发布审核后才进入正式模板库
```

现有 `POST /api/v1/agent/turn` 继续只负责门店资料收集，不加入模板组合语义。未来需要模型规划时使用独立契约，例如规划中的 `POST /api/v1/agent/template-plan`，不得直接改变 `agent-turn.v1`。

云端化时再按 NestJS 模块拆分：

- `TemplateRegistryModule`：已发布资产查询、兼容筛选和 Manifest 摘要；
- `CompositionModule`：组合校验、依赖解析、Lock、生成任务和报告。

本地优先阶段不提前建设注册表数据库。云端数据库只保存项目、组合规格、Lock、任务和发布元数据；组件源码由版本化可信发布包管理。

## 9. 预览、发布与后端能力

- 桌面 React 预览负责实时交互和快速反馈，以同一 CompositionPlan 为输入，但只称为效果预览。
- 正式导出和 Recipe 发布必须生成真实微信原生工程，并通过微信开发者工具编译及核心链路验证。
- Manifest 必须声明后端能力。广告排期、优惠券领取/核销等接口未实现时，只能 `preview-only`，并写入 `docs/后端待实现接口清单.md`。
- 金额继续只用整数分，业务金额由服务端计算；前端组件只负责展示。
- 模板、图标和生图资源是不同资产，生成任务不得绕过密钥和用户确认边界。

## 10. 验证策略

### 组件级

- Manifest、属性和事件 Schema 校验；
- 禁止 API、全局业务状态和固定路由的静态检查；
- 独立示例、空数据、异常数据、长文本和资源失败测试。

### 组合级

- 缺依赖、冲突、非法插槽、重复页面和路径逃逸的负例；
- 删除任一可选组件后 Base 仍可编译；
- 无真实后端能力的模块不能作为在线功能发布；
- 相同 Lock 结果可复现，失败无半成品；
- 每个组件与 Base、每个正式 Recipe、常见搭配和已知冲突均有测试，不追求全量笛卡尔积。

### 发布级

- 微信开发者工具真实编译；
- 核心点餐链路回归；
- 敏感信息扫描；
- 预览与导出使用同一组合规格；
- 发布报告记录版本、命令、结果和未解决问题。

## 11. 分阶段实施

| 阶段 | 范围 | 验收门槛 |
| --- | --- | --- |
| T0 契约冻结 | Base 边界、Manifest、CompositionPlan、插槽、Feature Pack、发布状态 | 规划与 Schema 评审通过，不写 Agent 组合代码 |
| T1 Base 验证 | 并入 B2，在 `miniprogram/` 完成核心闭环和核心组件 | B2 端到端通过，组件可删除性检查通过 |
| T2 本地 Composer | B2 后、B3 前，用固定 Plan 生成少量 Recipe，接通 Electron 导出 | 固定 Plan 可生成、微信编译、核心回归、相同 Lock 可复现 |
| T3 统一与扩展 | B3 统一模板源、联通门店配置；逐步增加海报轮播、营销区、广告位、优惠券 | 每资产独立验收，无后端能力不发布在线功能 |
| T4 Agent 与云端 | 独立组合规划契约、注册表/组合模块、项目和任务持久化 | Agent 只能选择白名单资产，生成结果经过同一 Composer 和测试 |

首批不追求组件数量，建议只打通：1 个 Base、2–3 个核心 UI Block、1 个海报轮播 Feature Pack、2–3 份 Recipe 和 1 个本地 Composer。
