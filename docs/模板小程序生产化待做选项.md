## 1. 使用规则

1. 用户按编号选择要实施的选项；未勾选不代表已排期，更不代表已实现。
2. 推荐包只是选择建议，不自动扩大当前答辩 MVP 范围。
3. 每项被采纳后，仍按“需求规格 → 技术设计 → 实施任务”评审；契约未确认前不编码。
4. 涉及真实微信支付、员工在客户端授权等当前冻结范围时，必须单独确认范围变更。
5. 完成后才能勾选对应选项，并填写代码、测试和真实运行证据；文档存在不能作为完成证据。
6. 新发现的真实代码缺陷若进入修复，应按 `docs/bugs/README.md` 登记；本清单不把未实现能力冒充 Bug。
7. 修改 Base 后必须同步评估镜像与 Composer 产物，不得只修 `miniprogram/`。

## 3. 产品决策选项

### D-01 商品详情加购行为

- [ ] 采用推荐方案：点击“加入购物车”后关闭详情，toast 提示成功，底部购物车同步更新；重复加份在列表步进器或购物车完成。
- [ ] 或采用连续加份方案：详情保持打开，但必须提供明显数量变化、成功反馈和常驻“去结算”按钮。

默认推荐：第一种。两种方案都必须补停售、达上限、存储失败等异常反馈。

### D-02 店主端形态

- [ ] 采用推荐方案：同一个原生小程序内提供角色化门店工作台。
- [ ] 或另行评审独立店主 App/小程序，需先证明持续后台运行、通知或设备能力确有必要。

默认推荐：先共用小程序，后端权限继续作为唯一安全边界。

### D-03 库存范围

- [ ] 采用推荐方案：首版只保留 `available`，表达“可售/售罄”，不宣称库存管理。
- [ ] 或新增真实库存：库存数量、扣减、取消回补、并发防超卖、预警和盘点必须作为独立项目设计。

默认推荐：基础小店首版不做数量库存，避免把布尔上下架误称为库存。

### D-04 支付范围

- [ ] 正式生产采用真实微信支付，包含回调、退款和对账。
- [ ] 或单独评审“到店付”经营模式；必须设计新的支付方式与订单状态规则，不得复用演示支付冒充真实交易。
- [ ] 当前阶段继续只做演示支付，明确不用于生产。

默认推荐：若目标确为正式线上生产，选择真实微信支付。

## 5. P1：门店日常运营必需

### P1-01 建立 OWNER/STAFF 权限矩阵和受控员工开通

- [ ] 推荐默认权限：
  - STAFF：查看本店订单、接单/推进、带原因取消、商品售罄/恢复、查看本店历史。
  - OWNER：包含 STAFF 全部能力，并独占商品新增/改价/删除、分类、门店设置、员工管理、数据和受控导入。
- [ ] 提供受控店主开通、员工邀请/绑定/解绑和角色调整；不允许公开自助成为店主。
- [ ] 若采用小程序内员工授权，先明确调整当前“客户端不授予角色”的范围约束。
- [ ] 所有接口按目标资源真实 storeId 重新校验角色，前端隐藏不作为安全措施。
- [ ] 验收：OWNER/STAFF/顾客/跨店/已解绑账号逐接口验证；首页多门店入口不能只取第一家。

### P1-02 商品与分类日常管理闭环

- [ ] 新增商品、编辑名称/描述/价格/分类/排序、上下架、软删除或等效安全删除。
- [ ] 分类新增、改名、排序、删除前归属检查。
- [ ] 商品价格使用整数 `priceCents`，服务端校验，历史订单仍使用快照。
- [ ] 商品更新带 `updatedAt` 或独立版本做乐观锁，避免多人覆盖。
- [ ] 商品/分类变更递增 `catalogVersion` 并失效目录缓存。
- [ ] OWNER 与 STAFF 权限按 P1-01 执行，关键变更保留操作者和时间。
- [ ] 验收：新增后立即出现在顾客端；改价只影响新订单；下架不可新加购；历史订单金额不变；并发修改返回冲突而不是静默覆盖。

### P1-03 商品图片上传与管理

- [ ] 支持商品图片选择、上传、替换、删除和失败重试。
- [ ] 使用 OBS 等服务端签名/临时凭证流程，密钥不进入小程序、导出工程、日志或仓库。
- [ ] 限制类型、大小、数量并做服务端校验；图片访问使用受控 URL。
- [ ] 顾客菜单和详情在图片失败时有稳定占位，不影响加购。
- [ ] 验收：真实上传、跨店引用、无效文件、超限文件、删除引用和弱网失败均覆盖。

### P1-04 重做订单工作队列和分页可达性

- [ ] 修复“只显示最早 50 单且没有后续页”的问题，采用可靠分页或游标，不允许漏单/重单。
- [ ] 默认队列拆为“新订单 `PENDING_ACCEPT` / 制作中 `PREPARING` / 待取餐 `READY` / 历史”。
- [ ] `PENDING_PAYMENT` 不占店主默认工作队列，可单独查询。
- [ ] 保留列表直接接单、制作完成、确认取餐和取消，不把详情变成必经页。
- [ ] 历史支持日期、订单号、桌号和状态查询。
- [ ] 验收：第 51、100、500 单均可达；新订单不会因升序第一页而隐藏；翻页、状态迁移和轮询组合下不漏单、不重复。

### P1-05 订单刷新、提醒和单卡处理状态

- [ ] 防止慢请求下每 10 秒轮询产生 in-flight 重叠；保留旧响应隔离和离开页面停止。
- [ ] 评估增量拉取或服务端推送；首版不得以引入 WebSocket 代替分页正确性。
- [ ] 新订单提供明显的数量/视觉提醒，前台声音提醒需有开关并考虑微信限制。
- [ ] 每个订单独立显示处理中，避免全页一个 `actingId` 阻断无关操作。
- [ ] 接单、拒单、完成、取餐提供防误触策略；取消继续强制原因。
- [ ] 状态冲突时刷新该卡并解释当前状态，不只显示通用错误。
- [ ] 验收：慢于轮询周期的响应、多店员同单/不同单、断网恢复、前后台切换均有确定行为。

### P1-06 真实桌台与桌码管理

- [ ] 菜单和结算统一使用后端真实桌号，不再依赖固定 A01/A02。
- [ ] 支持桌台新增、改名、排序、停用和桌码生成/打印/失效。
- [ ] 设计带门店隔离和防伪造能力的 scene/token；仅传公开 tableId 不应被描述为防伪。
- [ ] 桌码失效、跨店桌码、桌台停用和堂食未选桌均有明确提示。
- [ ] 验收：真实扫码得到正确门店与桌名，伪造/跨店/失效 scene 被服务端拒绝。

### P1-07 门店营业设置与下单执行

- [ ] OWNER 可维护门店资料、营业时间、临时打烊、堂食/自取开关。
- [ ] 创建订单时由服务端执行营业状态、履约方式和桌台校验，不能只用于展示。
- [ ] 顾客端明确展示营业状态和不可下单原因。
- [ ] 配置变更有版本、缓存失效和审计。
- [ ] 验收：打烊、非营业时段、关闭堂食/自取后，新订单被正确拒绝，已有订单查询不受影响。

### P1-08 历史订单与操作审计查询

- [ ] 店主可查询完成、取消和历史状态日志，查看操作者、时间、原因。
- [ ] STAFF 与 OWNER 可见范围按 P1-01 执行。
- [ ] 顾客只能看自己的订单，店主只能看本店订单。
- [ ] 验收：取消原因、状态冲突、跨店访问、分页和大数据量查询有测试。

## 7. 后端 agent 待实现接口建议

> 本节是接口方向，不是已冻结契约。采纳后先更新 `docs/api.md`、权限/订单/数据模型文档，再编码。现有接口保持不变，除非新契约明确废弃。

### 7.1 商品与分类

建议路由：

```text
POST   /api/v1/merchant/stores/:storeId/categories
PATCH  /api/v1/merchant/categories/:categoryId
DELETE /api/v1/merchant/categories/:categoryId
POST   /api/v1/merchant/stores/:storeId/products
PATCH  /api/v1/merchant/products/:productId
DELETE /api/v1/merchant/products/:productId
PATCH  /api/v1/merchant/products/:productId/availability   # 已存在，保留
GET    /api/v1/merchant/stores/:storeId/products          # 已存在，保留
```

实现要求：

- NestJS 独立 DTO、Guard、Service 和事务；所有目标资源按真实所属门店鉴权。
- 金额只接收整数 `priceCents`，拒绝浮点元、负数和后端不支持的总价字段。
- 创建接口支持 `Idempotency-Key`；更新接口携带版本/`updatedAt` 做乐观锁。
- 商品和分类变更与 `catalogVersion` 递增、缓存失效保持事务与最终一致语义。
- 删除优先软删除；历史订单快照不可变。
- 记录操作者、变更前后关键字段、requestId 和时间，改价必须可审计。
- 不用 OWNER 批量 imports 代替单项日常管理接口。

### 7.2 图片上传

建议路由：

```text
POST /api/v1/merchant/stores/:storeId/upload-credentials
```

实现要求：

- 返回短时、限定前缀/类型/大小的 OBS 上传凭证或签名，不下发长期密钥。
- 商品保存时校验图片归属、门店、对象存在性和可访问性。
- 防止跨店引用、任意路径覆盖、恶意文件和无限存储增长。
- 明确删除商品图片与回收 OBS 对象的生命周期。

### 7.3 员工与门店权限

建议路由：

```text
GET    /api/v1/merchant/stores/:storeId/members
POST   /api/v1/merchant/stores/:storeId/member-invitations
PATCH  /api/v1/merchant/stores/:storeId/members/:memberId
DELETE /api/v1/merchant/stores/:storeId/members/:memberId
```

实现要求：

- 仅 OWNER；邀请使用短时、一次性、绑定门店和角色的凭证。
- 防止删除最后一个 OWNER、越权提升角色和跨店绑定。
- membership 变更后 `/auth/me` 能刷新，所有写接口实时按数据库校验。
- 公开注册和客户端授权若仍是冻结红线，则先只实现服务端受控开通，不暴露客户端路由。

### 7.4 门店与桌台

建议路由：

```text
PATCH  /api/v1/merchant/stores/:storeId
POST   /api/v1/merchant/stores/:storeId/tables
PATCH  /api/v1/merchant/tables/:tableId
DELETE /api/v1/merchant/tables/:tableId
POST   /api/v1/merchant/tables/:tableId/qrcode
POST   /api/v1/merchant/tables/:tableId/qrcode/revoke
```

实现要求：

- OWNER 才能修改；营业与履约设置在下单事务中执行。
- 桌码 token 绑定门店和桌台、可失效，不能只信任客户端提交的 storeId/tableId。
- 桌台删除先检查订单引用，优先停用。
- 配置版本、缓存和公开门店信息同步更新。

### 7.5 订单队列与增量同步

现有接口：

```text
GET /api/v1/merchant/stores/:storeId/orders
```

建议增强：

- 支持游标或明确页码的完整 UI 可达性；过滤新订单、制作中、待取餐和历史。
- 默认工作查询不混入 `PENDING_PAYMENT`。
- 如采用 `updatedSince`，必须设计同时间戳 tie-breaker、分页、索引和状态迁移语义，避免漏单。
- 返回 `total`/游标和必要的服务端时间；列表数据避免无界增长。
- 状态推进继续保留 `expectedStatus`、条件更新和状态日志。

### 7.6 支付

支付契约必须单独立项，至少覆盖：

```text
POST /api/v1/orders/:orderId/wechat-payment
POST /api/v1/payments/wechat/notify
POST /api/v1/merchant/orders/:orderId/refunds
GET  /api/v1/merchant/stores/:storeId/payments/reconciliation
```

以上仅为职责提示，不能直接据此编码。必须先冻结商户订单号、金额、回调验签、幂等、状态机、退款和对账模型。

## 9. 当前不建议优先做的选项

- [ ] 真实数量库存：只有明确需要库存扣减和防超卖时再选。
- [ ] 规格、加料、套餐：先完成基础商品 CRUD，避免同时扩大订单报价模型。
- [ ] 外送/配送：仍不属于当前基础堂食/自取生产闭环。
- [ ] 独立店主 App：只有真实通知、后台运行或设备需求证明有必要时再评审。
- [ ] 复杂经营分析：先保证订单、商品、支付数据真实可靠，再做报表。
- [ ] WebSocket 全量推送：先修分页、漏单和轮询重叠，再决定是否需要推送。

这些“不建议优先”不等于永久取消，选中后仍需独立需求和契约评审。
