# 模板小程序生产可用性与门店运营调研报告

> 调研日期：2026-11-01  
> 调研角色：小程序产品、门店运营与生产可用性评审  
> 调研方式：静态代码核查、现有契约与测试记录复核、只读静态校验  
> 权威模板：`templates/base/ordering-base/1.0.0/src`；`miniprogram/` 是迁移期镜像，不是导出主链的唯一维护源  
> 配套待做清单：[`模板小程序生产化待做选项.md`](模板小程序生产化待做选项.md)

## 1. 执行摘要

### 1.1 总结论

当前模板已经具备**开发/答辩环境下的扫码点餐演示闭环**，不是只有静态页面：

- 顾客可以浏览菜单、加购、结算、创建订单、演示支付和查看订单。
- 店主/店员可以从“我的”进入门店工作台。
- 后端具有 Session、门店 membership、跨店权限校验、服务端计价、订单快照、创建幂等、六态状态机和状态日志。
- 店主/店员已经能在订单列表直接接单、制作完成、确认取餐和取消，不必进入详情页完成这些动作。
- 商品管理已经支持查看全部商品和上架/下架，并且会失效目录缓存。

但当前版本**不能直接判定为生产可用**。主要阻断不是视觉，而是：

1. 生成工程固定使用演示登录，生产后端会拒绝演示登录。
2. 只有演示支付，没有真实微信支付、验签回调、退款和对账。
3. production 导出仍存在 localhost 回退与安全扫描冲突，且实际 `storeId` 没有可靠注入。
4. 店主不能在日常工作台新增商品、改价、维护分类、上传图片或管理员工。
5. 店主订单台只取第一页 50 单，没有翻页；按创建时间升序时，新订单可能落在后续页而不可见。
6. 店主与店员除受控导入外，业务权限几乎相同，尚未形成运营所需的角色边界。
7. 真实桌码、营业/打烊、员工开通、真机高负荷和微信生产链路均未完成验收。

**可以实现生产级使用，且不需要推倒重来。** 现有 NestJS、MySQL、原生小程序、服务层和订单领域基础可以保留，但必须把“答辩 MVP”与“正式生产”拆成两个范围，完成 P0 主链路、P1 门店运营和真实设备验收后，才能宣称生产可用。

### 1.2 对本次问题的直接回答

| 问题 | 结论 |
| --- | --- |
| 店主能否自主上架产品？ | 能对已有商品上架/下架；不能从工作台新建商品。 |
| 店主能否修改价格？ | 日常小程序工作台不能；独立商品改价 API 也不存在。OWNER 受控导入可有限改价，但不等于日常运营能力。 |
| 店主怎么进入？ | 当前演示在“我的”切换演示店主/店员，再点击“门店权限”进入；正式链路应由真实微信登录后的 memberships 决定。 |
| 怎么区分店主和店员？ | 数据库有 `OWNER`、`STAFF`，页面显示角色；但订单和商品上下架权限相同，只有受控导入是 OWNER 专属。 |
| 是否有店主专属页面？ | 有 `merchant-orders` 工作台，但店主和店员共用；没有员工、门店设置、桌台、数据等 OWNER 专属页面。 |
| 详情页加购为什么不关闭？ | 代码明确只加购，不调用关闭；这是当前交互选择，不是事件丢失。 |
| 是否有人需要重复点同一道菜？ | 有多份需求，但不应以长期挡住菜单为代价；可用列表步进器、购物车改数量满足，详情默认“加购并返回”更高效。 |
| 点菜按钮是否没有作用？ | 正常可售商品的代码事件链完整；明确存在成功反馈弱、停售静默返回等“像没作用”的情况。当前设备若完全无反应，仍需微信运行时复验。 |
| 是否必须反复进入订单详情？ | 不是。列表已经能直接完成状态推进。真正问题是 50 单截断、全量轮询、缺少单卡处理中反馈和历史查询。 |
| 店主页面是否需要品牌个性化？ | 不需要跟随顾客端做品牌装修，但仍需要面向效率、防误触、可读性和安全区的专业工具型 UI。 |

## 4. 店主进入、身份和页面边界

### 4.1 当前演示进入路径

1. 打开“我的”。
2. 在“演示身份”中切换为演示店主或演示店员。
3. 页面根据登录结果中的 memberships 显示“门店权限”。
4. 点击对应门店，进入 `pages/merchant-orders/index?storeId=...`。

证据：

- `templates/base/ordering-base/1.0.0/src/pages/mine/index.js:58-78`
- `templates/base/ordering-base/1.0.0/src/pages/mine/index.js:115-121`
- `templates/base/ordering-base/1.0.0/src/pages/mine/index.wxml:23-39`

首页也存在店主入口，但只取 memberships 中第一家门店；多门店店主应统一使用门店选择列表，不能依赖首页的第一项。

### 4.2 正式身份链路的现状

后端已有真实 `wx.login code` 换 openid 的服务端实现，新微信用户默认只成为顾客，不会自动获得门店角色。店主和店员必须由受控流程预先建立 membership；当前种子数据用于演示。

Composer 却固定生成：

- `USE_WECHAT_CODE_LOGIN = false`
- 顾客、店主、店员三个 demo 身份

证据：`scripts/composer/emit.cjs:300-327`。小程序在该开关关闭时发送 `demoOpenId`，见 `templates/base/ordering-base/1.0.0/src/services/auth.js:15-23`；生产后端明确拒绝 demo 登录，见 `server/src/auth/auth.service.ts:37-69`。

所以：**后端存在真实登录代码，不等于生成工程已具备生产登录能力。**

### 4.3 当前权限矩阵

| 能力 | OWNER | STAFF | 说明 |
| --- | --- | --- | --- |
| 查看本店订单 | 可以 | 可以 | 后端校验门店成员 |
| 接单、制作完成、确认取餐 | 可以 | 可以 | 权限相同 |
| 取消订单 | 可以 | 可以 | 均需原因，无 OWNER 专属策略 |
| 查看全部商品 | 可以 | 可以 | 含下架商品 |
| 商品上架/下架 | 可以 | 可以 | 权限相同 |
| 新增商品、改价、编辑分类 | 不可以 | 不可以 | 日常业务 API 和 UI 都缺 |
| 受控导入 | 可以 | 不可以 | `StoreOwnerGuard` 明确限制 |
| 员工管理、门店设置、数据报表 | 无页面 | 无页面 | 未实现 |

`OWNER` 导入限制见 `server/src/common/auth/store-owner.guard.ts:33-44`；其他 merchant 操作只检查是否为本店成员，见 `server/src/merchant/merchant.service.ts:75-105,145-166,204-211`。

### 4.4 是否“只有店主该展示的页面”

当前只有一个店主/店员共用工作台，包含“订单台”和“商品管理”两个 tab。店主仍然处在顾客小程序内，可以继续访问顾客首页、菜单和自己的订单，这不是安全问题，也不是必须拆成两个 App 的理由。

真正需要满足的是：

- 页面入口按角色展示。
- 每个写接口在服务端重新校验角色和门店，不依赖隐藏按钮。
- OWNER 专属能力不暴露给 STAFF。
- 撤销 membership 后，刷新身份和后续 API 必须失效。
- 多门店切换不能串店。

现有跨店 Guard 是有价值的基础，应保留并扩展，而不是重写权限体系。

## 5. 商品和门店运营能力

### 5.1 当前商品管理实际能力

工作台商品页只有名称、描述、价格展示和上下架 switch，唯一修改操作是 `updateAvailability()`：

- `templates/base/ordering-base/1.0.0/src/pages/merchant-orders/index.wxml:100-145`
- `templates/base/ordering-base/1.0.0/src/pages/merchant-orders/index.js:359-381`
- `server/src/merchant/merchant.controller.ts:27-64`

完整 CRUD 并非“后端已有、前端缺入口”，而是前后端都未形成闭环。

### 5.2 生产能力矩阵

| 能力 | 当前状态 | 生产判断 |
| --- | --- | --- |
| 已有商品上架/下架 | 已有 UI + API | 可保留，适合“售罄/恢复供应” |
| 新增商品 | 无日常 UI/API | 必须补 |
| 修改名称、描述、价格、分类 | 无日常 UI/API | 必须补 |
| 分类新增、改名、排序、删除 | 无完整 UI/API | 必须补 |
| 商品排序 | 数据有 `sortOrder`，无维护闭环 | 必须补 |
| 商品图片 | 数据可存 URL，顾客端可展示 | 缺上传、替换、删除和资产管理 |
| 库存数量 | 数据模型没有，仅有 `available` | 基础小店可不做了；若承诺库存则须另建完整模型 |
| 操作审计与并发控制 | 商品更新无独立版本/审计 | 改价和多人运营前必须补 |
| 历史订单价格保护 | 有订单行快照 | 应保留，改价不得回写历史订单 |

OWNER 受控导入能创建部分商品/分类并在确认差异后改价，但有数量、字段和入口限制，且已有商品不会据此更新全部资料。它是部署/初始化工具，不应替代店主日常商品管理。

### 5.3 推荐的最低商品闭环

- 商品列表：搜索、按分类筛选、在售/下架状态、快速售罄。
- 商品编辑：名称、描述、整数分价格、分类、图片、排序、上下架。
- 新增商品：复用同一编辑表单，服务端校验并返回新业务对象。
- 分类管理：新增、改名、排序、删除前检查商品归属。
- 删除策略：优先软删除或下架，不物理破坏历史订单引用。
- 改价策略：只影响新创建订单；已创建订单继续使用快照，并明确待付款订单的价格与超时规则。
- 并发策略：使用 `updatedAt` 或独立版本号做乐观锁，避免两人互相覆盖。
- 权限策略：STAFF 可售罄/恢复，OWNER 才能新增、改价、删除和维护分类。
- 图片策略：使用 OBS 等服务端签名上传，密钥不得进入小程序或导出工程。

## 6. 顾客点餐交互评审

### 6.1 详情页加购后不关闭

代码路径明确：

1. 商品卡片打开详情，设置 `detailVisible=true`。
2. 详情组件触发 `add`。
3. 菜单页 `onDetailAdd()` 只调用 `addProduct()`。
4. 只有遮罩和关闭按钮会把 `detailVisible` 设为 `false`。

证据：`templates/base/ordering-base/1.0.0/src/pages/menu/index.js:190-213`。

这不是“按钮没有绑定”，而是当前产品行为。重复购买多份确实是真实需求，但现有列表和购物车已经有数量调整能力，没必要让详情弹层持续遮挡菜单来承载该需求。

**推荐默认行为：**

- 点击“加入购物车”后关闭详情。
- 显示明确成功反馈，如“已加入购物车”。
- 底部购物车数量和金额同步更新。
- 需要多份时，在列表步进器或购物车中继续增加。
- 停售、达上限、存储失败必须给出不同原因，不得静默。

若后续真实用户证明“详情内连续加份”高频，也可以保留弹层，但必须提供明显数量变化、成功反馈和“去结算”主按钮；不能保持目前弱反馈状态。

### 6.2 为什么用户会感觉“点菜没有作用”

正常可售商品的卡片和详情加购事件链都存在，购物车也会写本地存储。此前的微信运行时加购故障 BUG-017 已修复并复测，不能未经复现再次归因于同一原因。

当前代码仍能造成“没作用”的感知：

- 正常加购没有成功 toast，详情也不关闭。
- 商品 `available === false` 时，详情组件直接 return，没有原因提示。
- 商品 ID 缺失时同样静默 return。
- 达 99 份后不再增加，只有上限提示。
- 本地存储失败被底层吞掉，购物车层未检查保存结果，可能无错误反馈；此项是静态风险，需构造故障验证。

建议先补反馈与异常可观测性，再在微信开发者工具/真机复验。如果正常商品仍完全无反应，应记录 Console、商品 ID、`available`、本地存储和 `quantityMap`，不要只根据按钮外观定 Bug。

## 7. 店主订单交互与高峰风险

### 7.1 列表已经支持完整推进

当前列表卡片可以直接执行：

- `PENDING_ACCEPT`：接单制作、拒单取消。
- `PREPARING`：制作完成、取消。
- `READY`：顾客已取餐、取消。

证据：

- `templates/base/ordering-base/1.0.0/src/components/order-card/index.wxml:33-43`
- `templates/base/ordering-base/1.0.0/src/pages/merchant-orders/index.js:315-356`
- `server/src/merchant/merchant.service.ts:75-142`

因此，“每个订单都必须进入详情才能完成流程”的前提不成立。详情页适合查看完整信息，不应成为常规接单必经页；后续设计应继续强化列表操作，而不是把用户引导回详情。

### 7.2 真正的高峰阻断：50 单之后不可见

店主页固定请求 `pageSize:50`，不传后续页，WXML 没有加载更多或页码；后端按创建时间升序返回：

- `templates/base/ordering-base/1.0.0/src/pages/merchant-orders/index.js:169-199`
- `templates/base/ordering-base/1.0.0/src/pages/merchant-orders/index.wxml:65-98`
- `server/src/merchant/merchant.service.ts:55-64`

当当前分段超过 50 单时，只显示最早 50 单，新订单可能在第二页而完全不可见。待付款订单还与待接单订单混在“待处理”中，但店主不能处理待付款订单，会进一步挤占工作队列。

这是订单高峰期的高优先级能力缺口，应先于视觉优化解决。

### 7.3 轮询与操作反馈问题

- 每 10 秒重新请求当前分段第一页并整份 `setData`。
- 请求慢于 10 秒时没有 in-flight 去重；请求序号只丢弃旧响应，不阻止重复请求。
- 每个列表包含全部订单行项目，卡片展开渲染全部菜品。
- 全页只有一个 `actingId`，任意订单处理中会阻止其他订单操作。
- 店主卡片没有接收处理中属性，点击后缺少单卡进度反馈。
- 接单、完成和取餐没有二次确认；误触后直接改变真实状态。
- 只有“待处理/进行中”，缺少新订单、待取餐、历史、已取消和搜索视图。

**推荐订单台信息架构：**

1. 新订单：只放 `PENDING_ACCEPT`，突出接单和拒单。
2. 制作中：放 `PREPARING`，主操作为制作完成。
3. 待取餐：放 `READY`，主操作为确认取餐。
4. 历史：完成/取消，支持日期、订单号、桌号查询。
5. 待付款不进入店主的默认工作队列，可单独查询，不占新订单数量。

首版应先做可靠分页/游标、请求去重、单卡 loading、新订单提示和列表快捷操作，再评估 WebSocket 等推送方案。不能为了“实时”直接引入复杂推送，却仍保留漏单和重复请求问题。

## 8. 店主端 UI 方向

用户判断“店主页面不需要顾客向的 UI 个性化”是合理的，但要区分：

- **不需要品牌装修**：不需要渐变 Banner、营销文案、主题换肤和装饰性卡片。
- **仍然需要工具型体验设计**：订单密度、状态识别、触控面积、防误触、异常反馈、断网恢复和单手操作都直接影响营业。

当前店主页部分读取顾客主题 Token，同时头部使用固定深绿渐变，switch 仍有硬编码橙色，见 `templates/base/ordering-base/1.0.0/src/pages/merchant-orders/index.wxss:5-10,94-167` 和 `index.wxml:16-21,134-140`。

建议：

- 店主端使用独立、固定的中性色设计 Token，不随门店主题变化。
- 优先高密度列表、清晰主按钮、明确状态文本和异常颜色。
- 状态不能只用颜色表达，必须同时有文字。
- 保留必要留白和安全区，但不设置营销型头部。
- 列表默认展示完成当前动作所需信息，详情只承载次要信息。
- 关键操作提供处理中、成功、失败和冲突反馈。

## 9. 生产级差距清单

### 9.1 P0：生产主链路阻断

| 缺口 | 证据与影响 |
| --- | --- |
| production 登录不可用 | Composer 固定 demo 登录，生产后端拒绝 demo；见 `scripts/composer/emit.cjs:300-327`、`server/src/auth/auth.service.ts:37-69` |
| production 支付不存在 | 只有 `demo-payment` 和 `UNPAID/DEMO_PAID`；生产禁用 demo 后，订单无法按现有规则进入可接单状态 |
| production 导出安全扫描冲突 | 生成代码和 README 带 localhost 回退，production 安全扫描会报 `LOCALHOST_IN_PRODUCTION`；见 `scripts/composer/emit.cjs:236-245,300-315`、`scripts/composer/safety.cjs:87-104` |
| 实际门店绑定不可靠 | 生成配置未写入真实 `store.id`，环境回退 `store-demo-001`；见 `scripts/composer/emit.cjs:172-179,310-312` |
| Agent 生产鉴权缺陷 | 已有 BUG-007，任意形式正确的 Bearer 可能通过 Agent Guard；不能因“生产要求鉴权”而视为安全 |

真实支付和客户端角色授予超出当前答辩 MVP 范围，采纳时必须显式调整范围，不能悄悄把 demo 开关当成生产方案。

### 9.2 P1：日常营业必需

- 商品与分类日常 CRUD、改价、排序、图片和并发保护。
- OWNER/STAFF 权限矩阵、员工受控开通/解绑和角色刷新。
- 订单分页/游标、工作队列拆分、请求去重、单卡反馈和新订单提醒。
- 真实桌号列表、桌码生成/打印/失效、门店隔离和 scene 防伪造策略。
- 门店营业/临时打烊和履约开关由服务端在下单时执行。
- 历史订单、取消原因和状态日志查询。
- 真机 HTTPS、合法域名、多店员并发和高峰订单验收。

### 9.3 P2/P3：效率、运营与治理

- 商品详情加购后的统一反馈与关闭策略。
- 店主端固定工具型 UI，与顾客主题解耦。
- 多门店选择、营业额/销量等基础报表。
- 库存数量、规格、加料等应按真实业务另立范围；基础小店不能被迫一次性实现。
- 完成 Base/镜像迁移，避免后续修复只落在其中一份工程。
- 云资源、备份恢复、监控、告警、回滚和发布流程按既有 M9 路线验收。

## 10. 推荐目标形态

### 10.1 应用形态

建议第一阶段继续使用**同一个微信原生小程序 + 角色化门店工作台**，不急于拆独立店主 App。是否拆端应由真实设备、消息通知和持续后台运行需求决定，而不是为了视觉上的“店主感”。

### 10.2 店主/店员页面

OWNER 可见：

- 订单工作台。
- 商品与分类管理。
- 桌台与桌码。
- 门店营业设置。
- 员工与权限。
- 历史订单和经营数据。

STAFF 默认可见：

- 订单工作台。
- 商品售罄/恢复。
- 本店历史订单。

STAFF 默认不可见或不可操作：

- 改价、新增/删除商品、分类维护。
- 门店设置、员工管理、经营数据。
- 受控导入。

所有限制必须由后端执行；前端隐藏只用于减少干扰。

## 11. 建议实施顺序与验收门槛

1. 先选择待做清单中的范围，明确是否从答辩 MVP 进入正式生产阶段。
2. 先修 production 导出、真实登录、真实门店绑定和 Agent 鉴权。
3. 并行推进订单高峰可靠性与商品运营闭环，但接口契约须先评审。
4. 补角色、员工、桌码和营业设置。
5. 做顾客加购反馈与店主工具型 UI。
6. 最后以真实微信凭据、真实支付、真机、51/100/500 订单、多店员和跨店越权测试验收。

任何阶段都不能用以下证据代替生产验收：

- 静态校验通过。
- Node mock 测试通过。
- React 预览正确。
- demo 登录/支付成功。
- 文档或接口定义已经存在。

## 12. 最终判断

当前模板是一个**有真实业务后端基础的演示 MVP**，不是空壳，也不是生产系统。现有订单、权限、计价和快照设计值得保留；最需要优先补的是生产登录/支付/导出、商品日常管理、订单高峰可达性和角色边界。
