# 桌面生成器云端接口清单（后续阶段）

> 本文覆盖桌面生成器的项目/会话、候选、提示词、生图、部署、模板注册表和组合生成等后续接口，不是点餐业务后端的首期清单。统一路线见 [`后端实现方案与套餐.md`](后端实现方案与套餐.md)，模板组合架构见 [`模板库与组合生成规划.md`](模板库与组合生成规划.md)，顾客/店主 API 契约见 [`api.md`](api.md)。除第 15 节明确标记已实现的 `agent/turn` 外，其余接口均为规划；桌面端当前由本地服务或占位实现支撑。
> 技术栈约定：NestJS 模块化 + MySQL（RDS）+ Redis（DCS），API 使用 `/api/v1` 版本化风格；订单/商品金额以整数「分」存储与传输，金额由服务端计算。

## 1. 通用约定

- Base URL：`/api/v1`，JSON，`camelCase`。
- 认证：店主登录后 `Authorization: Bearer <JWT>`。
- 错误结构：

```json
{ "code": "PROMPT_ROUND_INVALID", "message": "人类可读说明", "details": {} }
```

- 幂等：创建类请求支持 `Idempotency-Key` 头。
- 分页：`page` / `pageSize`，响应 `{ items, page, pageSize, total }`。
- 时间：ISO 8601 字符串。
- 金额：整数分（如 `2800` 表示 28.00 元），前端不传总价。
- 长任务：统一异步任务模型 `{ taskId, status, progress, result?, error? }`，状态 `queued | running | succeeded | failed | canceled`。

前端调用：`generateImage` / `reviseImage`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/v1/generation/images` | 创建生图任务 |
| GET | `/api/v1/generation/images/:imageId` | 查询任务状态 |

创建响应：

```json
{ "imageId": "01J...", "status": "queued", "progress": 0 }
```

```json
{
  "imageId": "01J...",
  "status": "succeeded",
  "progress": 100,
  "imageUrl": "https://obs.example.com/...",
  "provider": "huawei-modelarts",
```

- 图片存 OBS，返回可过期签名 URL；不要把 base64 长期存 DB。

## 10. Redis 用途建议

- 会话当前 phase 与最近消息缓存（降低 MySQL 读压力）。
- 异步任务状态与进度（TTL 与任务生命周期一致）。
- 幂等键（`Idempotency-Key` → 结果）。
- 接口限流（按 owner / IP）。
- SSE 事件通道（如需实时进度）。

## 12. 安全与合规

- 模型密钥、OBS 凭证、数据库密码只放服务端环境变量，禁止进入仓库或前端。
- 门店参考图上传前必须用户确认；明确告知发送范围。
- 不代办微信主体注册、认证、审核、发布。
- 会话与图片按 owner 隔离，接口需校验归属。
- 日志脱敏，不记录完整提示词中的敏感经营信息（可按需保留摘要）。

## 15. Agent 资料收集（`POST /api/v1/agent/turn`）

> 状态：**已实现（真实 Provider：DeepSeek）**。桌面端通过 `VITE_AGENT_TRANSPORT=http` 切换；默认仍为本地 Mock。
> **ModelArts / 盘古尚未接入**；没有 Skill、工具调用、多 Agent、自主规划和自动发布。
> 完整字段、错误码与配置见 [`agent-turn-contract.md`](agent-turn-contract.md)；历史验证记录见 [`handoff/archive/2026-10-31-Agent资料收集与DeepSeek接入.md`](handoff/archive/2026-10-31-Agent资料收集与DeepSeek接入.md)。

### 15.1 能力定位

这是**开店资料收集**能力，不是点餐业务接口，也不是项目/会话持久化接口：

| 对比项 | `agent/turn` | `store-projects` / `generation/*` |
| --- | --- | --- |
| 目的 | 从店主自然语言提取结构化开店资料草稿 | 项目持久化、模板匹配、提示词、生图 |
| 写入 | **店主确认前不写库** | 项目/任务持久化 |
| 身份 | 未来店主鉴权 | 店主鉴权 |
| 会话 | 单轮 `turnId`；不得复用 B1 `sessions` | 项目 ID / 任务 ID |
| 模型 | 只抽取与草拟 | 生图/对话模型 |

禁止把 B1 顾客登录的 `sessions` 表当作 Agent 会话表。若后续需要持久化，应新增 `agent_sessions` / `agent_turns` 独立表并单独立项。

### 15.2 请求与响应

- `POST /api/v1/agent/turn`，JSON，`/api/v1` 版本化。
- 请求：`contractVersion='agent-turn.v1'`、`utterance`（1–500 字）、`draft`（`ContractDraft`）、`client.surface='desktop'`、`client.phase='store-info'`、`projectId=null`。
- 响应：`contractVersion`、`turnId`、`status`（`collecting|reviewing`）、`reply`、`draft`、`missingFields`、`errors`、`nextQuestion`、`meta`。
- 金额只传 `priceCents` 整数分；`priceText` 不进入契约。
- `meta.mock=true` 时必须明确标识未调用真实模型；真实接入后 `meta.mock=false` 且 `meta.model` 为真实模型标识。

## 16. 模板注册表与组合生成（规划，本地 Composer 验收后实施）

本节不代表当前后端已经支持动态模板或代码生成。第一阶段注册表与组件源码共同存放在 Git，本地 Composer 验证前不创建数据库注册表。

### 16.1 模块边界

- `TemplateRegistryModule`：查询已发布 Base、UI Block、Feature Pack、Recipe 和 Manifest 摘要，按兼容性与发布状态筛选。
- `CompositionModule`：校验 CompositionPlan、解析依赖/冲突、生成 Lock、创建组合任务和保存验证报告。
- Agent 组合规划使用独立契约，例如 `POST /api/v1/agent/template-plan`；不得改变已冻结的 `agent-turn.v1`。

### 16.2 候选接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/template-registry` | 按 Base、兼容版本和发布状态查询 Manifest 摘要 |
| POST | `/api/v1/compositions/validate` | 校验 CompositionPlan 并返回规范化结果或问题 |
| POST | `/api/v1/compositions/compile` | 创建确定性生成任务，输入不包含源码或秘密 |
| GET | `/api/v1/compositions/:taskId` | 查询任务、Lock、产物和验证报告 |

以上路径均为规划契约，实施前须在 API 文档中冻结请求/响应和错误码。生成源码只能来自可信版本化资产；数据库保存项目、Plan、Lock、任务和发布元数据，不把模型生成源码作为可信资产写入。

### 16.3 验收清单

- [ ] 文件注册表与云端发布元数据有清晰同步方向，无双事实写入。
- [ ] 非法版本、依赖、冲突、插槽和路径在生成前拒绝。
- [ ] 相同 Lock 可复现，任务失败可重试且无半成品。
- [ ] `preview-only` 资产不能发布为在线能力。
- [ ] Agent 无法通过提示词注入引入未登记组件、源码或密钥。
- [ ] 云端产物经过与本地相同的组件、组合和微信编译验证。
## 17. B2 发现的点餐接口缺口（建议，未实现）

这些缺口来自 2026-10-31 B2 小程序实施，当前前端均已用本地兜底完成演示；不阻塞 B 套餐验收。若采纳，必须先改 `docs/api.md` 再改实现。

### 17.1 公开桌号列表

现状：契约只有 `GET /stores/:storeId` 与 `/catalog`，没有桌号数据。小程序堂食只能从扫码 `scene` 拿 `tableId`，开发者工具里用「演示桌号 A01/A02」兜底，无法列出真实桌台。

建议：

```http
GET /api/v1/stores/:storeId/tables
```

```json
{
  "storeId": "store-demo-001",
  "tables": [
    { "id": "tbl_A01", "name": "A01", "sortOrder": 1 }
  ]
}
```

- 公开接口，无需登录；门店不存在 `404 STORE_NOT_FOUND`。
- 只返回该门店桌号，不返回任何订单或占用状态。
- 实现落点：`server/src/stores`（新 DTO/投影）；数据量小，无需缓存。
- 前端改造：`pages/home` 用真实桌号替换 `config/env.js` 的 `DEMO_TABLES`；保留演示兜底作为开发环境的可选行为。
- 验收：S1 缺桌号仍拒绝；S2 跨店桌号仍 `TABLE_NOT_FOUND`；前端可选择本店桌号并成功下单。

### 17.2 扫码 scene 携带桌号名称

现状：`scene` 只解析 `storeId/tableId`，桌号名称靠前端本地表或订单返回值。若二维码由门店动态生成，建议 `scene` 直接带 `tableName`。

建议：约定 `scene=storeId=..&tableId=..&tableName=..`，前端解析即可，**不需要新增后端接口**，但需要在门店二维码生成流程中固化。若二维码由后端生成，应新增受控的桌码生成/下载接口，属于 B3 范围。

### 17.3 顾客订单跨店聚合（可选）

现状：`GET /orders` 要求必填 `storeId`，顾客只能看当前门店订单。演示单店时无影响。

建议：

```http
GET /api/v1/orders?page=1&pageSize=20&active=true   # 省略 storeId
```

- 只返回当前用户自己的订单，按 `createdAt` 倒序；`storeId` 可选，传入则仍按门店过滤。
- 订单对象已包含 `storeId / storeName`，无需新字段。
- 实现落点：`server/src/orders/orders.service.ts` 的 `listForCustomer`，调整 `storeId` 必填校验与查询条件。
- 风险：会影响 B1 测试用例（`b1-orders.test.ts` 中 storeId 必填断言），需同步修订。

### 17.4 店主订单台增量拉取（可选）

现状：小程序每 10 秒全量拉取当前分段最多 50 条，演示量级足够。

建议：`GET /merchant/stores/:storeId/orders?updatedSince=<ISO>`，仅返回 `updatedAt >= updatedSince` 的订单；或返回 `version` 供前端做条件请求。实现前需明确状态变更与更新时间的索引和分页语义，避免漏单。

### 17.5 验收边界

- 以上均为**建议**，未写入 `docs/api.md`，当前后端不得被描述为已支持。
- 17.1 是唯一直接影响真实堂食演示体验的缺口；17.2–17.4 可按答辩时间取舍。
- 前端兜底位置：`miniprogram/config/env.js` 的 `DEMO_TABLES`、`miniprogram/domain/scene.js`、`miniprogram/pages/home/index.js`。
## 18. P0 之后的后端候选（建议，未实现）

> 本轮桌面 P0（项目持久化 / 设置自检 / 导出交接 / 支付结果页）没有改 server。以下为实施中发现、但不属于本轮范围的候选；采纳前需单独评审并更新 `docs/api.md`。

### 18.1 Agent 只读健康端点（优先级：P2，可选）

**现状**：桌面设置页的「模型通道」自检只校验 `agentEndpoint` 格式并复用 `GET /api/v1/health` 判断后端存活，**不发起真实 turn**（避免消耗额度与写入数据）。因此无法区分「后端活着但 DeepSeek Key 未配置 / 已失效」。

**建议**：新增 `GET /api/v1/agent/health`，要求：

- 只读：不调用 DeepSeek、不写数据库、不产生订单或会话数据。
- 返回结构（建议）：

```json
{
  "status": "ok",
  "contractVersion": "agent-turn.v1",
  "provider": "deepseek",
  "configured": true,
  "transport": "http"
}
```

- `configured` 只表示服务端是否读到 `DEEPSEEK_API_KEY`（**只返回布尔，绝不返回 Key 或其长度/前缀**）。
- `provider` 从现有 Provider 配置读取；未配置时返回 `configured: false` 且 HTTP 200（不是 503，避免把「未配置」当「服务挂了」）。

**前端落点（已预留）**：`src/services/diagnosticsService.js` 的模型通道行可改为调用该端点；当前先保持复用 `/health`。若后端不实现，本轮行为不变，不视为缺陷。

**风险**：新增路由属于后端契约增量，需要 `server` 侧测试与 `docs/api.md` 同步；不影响现有 `POST /agent/turn`。

### 18.2 项目云端同步（优先级：P3，明确不做）

桌面 P0 的项目数据是本机 `userData/projects/<id>/project.json`。若后续要多端协作，需要：

- 项目 CRUD 与增量同步接口（含并发版本/冲突合并）。
- 图片资产上传（OBS）与引用重写。
- 账号体系与项目归属。

这超出当前「答辩 MVP + 本机生成器」定位，本轮只登记，不设计契约。

### 18.3 门店 / 分类 / 商品写接口（优先级：P2，菜单编辑器前置）

方案 2.2 已明确：菜单编辑走「后端 imports apply」路线，前置条件是补门店资料更新、分类增删改、商品增删改与排序、桌号维护。当前 B3 imports 已具备 preview/apply 与幂等，但只支持「1 个默认分类 + 扁平菜品」。若后续要做桌面菜单编辑器，需要先补这些写接口与 `catalogVersion` 递增语义；本轮不做。

### 18.4 门店自主运营与生产化接口（2026-11-01 调研，未实现）

> 详细选项、权限矩阵和验收口径见 [`模板小程序生产化待做选项.md`](模板小程序生产化待做选项.md)。当前均为建议，未写入 `docs/api.md`，不得描述为已支持。

- **商品与分类**：补单项新增、编辑、改价、排序、软删除和分类维护；保留已有上下架接口。金额使用整数 `priceCents`，更新带版本/乐观锁，变更递增 `catalogVersion` 并失效缓存，历史订单快照不变。
