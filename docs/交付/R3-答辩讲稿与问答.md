# R3 答辩讲稿、提纲与高频问答

## 1. 三分钟讲稿

各位评委好，我们的作品是“口袋店长·轻启”。它解决的是餐饮小店数字化开店中三个具体问题：需求表达和工程实现之间有门槛，修改过程难追踪，生成结果难交付、难恢复。

我们的核心不是让模型直接写一套任意代码，而是把流程拆成三层：**统一 Agent 理解需求，受约束的 DSL / Recipe / Lock 表达和冻结计划，确定性 Composer 生成工程。** 店主在任意项目阶段都使用同一个会话入口；模型只能提交结构化提案，字段写入经过白名单、校验和桌面状态机，高风险操作仍走人工确认。

演示主线中，AI 能把一段自然语言整理成门店资料、营业时间与菜品；两套模板具有可见的结构差异，模板修改有明确的 before/after，并可撤销。海报通过第三方 imagelfk 服务、gpt-image-2.6 模型真实生成，选用后持久化，并作为本地资产进入正式导出包。

正式导出不是一张效果图，而是一份完整微信小程序工程。我们已在微信开发者工具中真实运行，验证四页、桌台选择、加购、购物车、结算和后端订单；订单能从 UNPAID 进入 DEMO_PAID。这里的支付是演示支付，不是真实交易。应用内微信预览也已补齐同一海报资产。

工程方面，项目资料、素材与进度本地落盘，可重开恢复；导出计划带摘要锁，同名目录不覆盖，密钥不进入页面、导出工程或证据。R2 测试 1251/1251 通过，构建与镜像检查通过，但测试数量只作为回归保障，不代替真实运行证据。

我们也明确边界：真机、发布、真实支付和华为云均未执行，不在本次交付范围。参考截图重构是实验支线，当前版本仍 BLOCKED，主演示完全不依赖它。我们的交付重点是可验证、可恢复、边界诚实的开店工程闭环。

## 3. 高频问答

### Q1：你们解决的核心问题是什么？

不是“再做一个页面生成器”，而是把小店需求变成**可确认、可撤销、可持久化、可正式导出的工程**。自然语言只是入口，最终价值是受控状态流转和真实交付闭环。

### Q2：统一 Agent 统一在哪里？

资料、模板等阶段共用同一个会话入口、请求上下文和桌面状态机；服务端只返回 proposal / needs-input / rejected，不能把 proposal 当已写入。字段能力目录有唯一事实源，避免不同页面各写一套限制。

### Q3：为什么不让大模型直接生成任意 WXML/WXSS/JS？

任意代码难以约束安全、结构、资产和可复现性。本项目让模型只在允许范围内产出结构化意图，再由 DSL、Recipe 和 Composer 落地。这样能做字段校验、白名单、摘要锁和确定性生成，也更容易撤销与审计。

### Q4：DSL、Recipe、Lock 各自解决什么？

- DSL：描述有界的页面/视图需求，不开放任意命令或源码执行。
- Recipe：选择并组合已注册的模板与能力，明确结构及参数。
- Lock：冻结实际生成计划和产物摘要，用于一致性校验和复现；内容变化后旧体检/旧摘要不能继续冒用。

### Q5：海报是真 AI 生成还是预置图片？

R1 已真实调用第三方 imagelfk，模型 gpt-image-2.6，生成后选用并持久化，正式导出包含实际 PNG 和来源清单。用户上传素材会标为用户上传，不冒充 AI。现场服务若失败，会明确使用已验收资产，不伪称现场生成。

### Q6：真实生图资产如何证明“入包”？

正式导出目录存在 `assets/media/home-background.png`，首页 WXML 引用该路径；D2 还对新应用内预览副本与正式导出做了 sha256 一致性检查。证据不是只有桌面预览图。

### Q7：React 预览、微信预览和真机有什么区别？

React 预览用于桌面端快速确认布局；应用内微信预览会生成新鲜工程副本并交给微信开发者工具；真机是在物理设备运行。前两者都不是真机。本次真机 NOT_RUN。

### Q8：你们完成支付和发布了吗？

没有。只验证演示支付状态 `UNPAID → DEMO_PAID`，不发生资金交易；未上传、未发布、未提审，真实支付 NOT_RUN。测试号运行不能作为发布证据。

### Q9：工程创新体现在哪里？

统一会话与桌面 reducer 的提案/写入分离，字段能力单一事实源，受约束生成与 Lock 摘要，真实资产受控入包，本地可恢复项目，以及对预览、导出、微信、真机、发布的证据分级。创新点是完整可信闭环，而非单一模型调用。

### Q10：竞赛创新体现在哪里？

把自然语言开店、可视化模板差异、可撤销修改、真实 AI 物料和微信真实业务交互放进同一条短链路；同时把失败、未执行和实验支线明确展示，避免“看起来能跑、实际不可交付”。

### Q11：数据安全怎么做？

模型没有任意文件/命令工具；写入经过白名单与校验，高风险动作仍需确认。密钥只在本机安全配置中，不进渲染页面、文档、日志、导出包或 Git。导出不自动上传发布。海报提示词中的店名、品类等文字会发送给第三方 imagelfk，界面在生成前披露。

### Q12：是否完全离线、能否本地部署？

桌面项目、数据库、Composer 与正式工程均可本机运行和保存；但“本地部署”不等于“完全离线”：真实 Agent 与 AI 生图需要各自外部模型服务，MySQL 为本机依赖，Redis 可降级为 memory。网络或上游失败时应如实报错，不伪装成功。

### Q13：测试结果怎样？

R2 根目录 `npm test` 为 1251/1251，通过；Vite/Nest 构建、契约、能力、小程序与镜像检查通过。R1 另有真实微信编译和交互证据。R3 为冻结整理，没有重跑这些项目，也不把测试数当作真机或发布证明。

### Q14：截图识别/重构是否可用？

当前版本 BLOCKED。冻结基线多次真实运行均未在 8 次模型调用内产出合法候选，因此候选验证、采用和导出不能宣称通过。历史 T6 是另一轮历史证据，不代表当前。主演示不使用该支线。

### Q15：是否用了华为云？

没有。华为云 NOT_RUN、非本次依赖。真实生图服务是第三方 imagelfk，模型 gpt-image-2.6。

### Q16：目前最重要的限制是什么？

真机、发布和真实支付未验证；AI 生图依赖第三方服务；截图重构仍 BLOCKED；当前验证以本机 Windows 环境为准。后续应分别作为独立里程碑验收，不能用已有主线 PASS 推导它们也通过。
