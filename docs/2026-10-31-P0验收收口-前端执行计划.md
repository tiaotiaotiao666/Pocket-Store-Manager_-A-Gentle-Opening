## 五、F1：导出目标冲突预检

### 5.1 目标行为

在已知 `parentDir + projectName` 时，先以只读 IPC 判断最终目标是否已存在：

- 已存在：体检面板出现 `E-TARGET-EXISTS`，不调用 `composer:export`，不创建 staging，不修改任何已有目录。
- 不存在：允许继续；真正导出仍保留 Composer 自己的 `TARGET_EXISTS` 二次保护，以覆盖预检后目录被其他进程创建的竞态。
- 尚未选择目录：不伪造目标路径，不显示目标冲突；其余本地规则与 Composer validate 正常执行。
- 浏览器模式：仍由 `E-DESKTOP-REQUIRED` 阻断，不调用新 IPC。
- 冲突发生后：用户必须能重新点击“选择/更换导出位置”；不能因为 `selectCanExport === false` 而永久禁用唯一的解冲突入口。

### 5.2 主进程 IPC 契约

新增通道：`composer:preflight-target`。

请求：

```json
{
  "parentDir": "C:\\Users\\example\\AppData\\Local\\Temp\\smartstore-p0",
  "projectName": "松月食堂"
}
```

成功返回：

```json
{
  "ok": true,
  "exists": false,
  "projectName": "松月食堂",
  "suggestedName": null
}
```

冲突时仍返回 `ok: true`、`exists: true`，并可返回只读计算出的 `suggestedName`；是否冲突由 `exists` 表达，不与 IPC 传输失败混为一谈。父目录缺失、参数非法或检查失败时返回 `ok: false` 和稳定错误码。

实现约束：

1. 在 `desktop/composer-ipc.cjs` 注册 handler，沿用 `isTrustedSender` 和 payload 体积限制。
2. 使用与 Composer 相同的 `sanitizeProjectName` 计算目标名，避免渲染层和主进程清洗规则不一致。
3. 只做 `path.resolve` / `path.join` / 存在性读取等只读操作；不要直接复用 `scripts/composer/atomic.cjs` 的完整 `preflight()`，因为其中的 `canWrite()` 会创建并删除 probe 文件，不符合本通道“只读”的定义。
4. 不创建父目录、目标目录、staging、probe 或报告，不调用 `compose`。
5. 不因预检成功就把路径写入 `exportedOutputs`，也不扩大 AppID 后置写入允许范围。
6. 在 `desktop/preload.cjs` 只新增一个白名单方法，例如 `composerPreflightTarget(payload)`；不暴露 `ipcRenderer`、任意路径读取或 `fs`。

### 5.3 渲染服务与规则合并

在 `src/services/exportService.js` 新增 `preflightTarget({ parentDir, projectName })`：

- 桌面桥接不存在时返回 `desktop-required`。
- 正确透传参数并区分“检查成功”“冲突”“检查失败”。
- 不把检查失败静默当作“不存在”；失败必须阻断本次导出并显示可读原因。

在 `src/domain/preflightRules.mjs` 增加纯函数形式的目标结果合并逻辑：

- `exists: true` 时追加且只追加一条 `E-TARGET-EXISTS`。
- `fieldPath` 使用 `deploy.projectName` 或 `projectName`，全批保持一致。
- 文案明确“目标目录已有同名工程，不会覆盖；请更换导出位置或项目名”。
- 将 `E-TARGET-EXISTS` 加入 error 规则 ID 清单。
- `exists: false` 不产生 error；重复合并同一结果不产生重复行。

### 5.4 App 接线与防死锁

在 `src/App.jsx` 两条路径都接入：

1. **常规体检**：`runPreflight` 完成本地规则和 Composer validate 后，若当前已有 `deploy.directory` 与有效项目名，则调用目标预检并合并结果。
2. **选择目录后的导出前检查**：`runDeployExport` 在调用 `exportProject` 前再次检查刚选择的目录。冲突时更新体检面板并进入现有冲突/失败的可恢复状态，不调用 Composer 导出。

状态与按钮要求：

- 保留 `selectCanExport` 的语义：只要存在 `E-TARGET-EXISTS`，仍然“不可直接导出”。
- 另设“是否允许选择/更换目录”的派生判断，供 `handleDeployChooseDirectory` 和 `DeployStep` 的 `blockedReason` 使用。
- 当唯一新增阻断是 `E-TARGET-EXISTS`，且其他 error 为零、warn 均已确认时，允许重新选择目录；选择后仍必须通过新目标预检才能真正导出。
- 若还有其他 error 或未确认 warn，继续禁用，不能借“更换目录”绕过其他门禁。
- 不通过全局忽略 `E-TARGET-EXISTS` 的方式让 `selectCanExport` 返回可导出。
- 预检与导出之间状态必须收敛，不能停留在 `choosing`、`validating` 或 `busy: true`。

## 六、F2：工作台真实缩略图

### 6.1 目标行为

- 桌面模式下，项目卡片显示该项目 `thumbnailAssetId` 对应的真实图片缩略图。
- 无图片、图片索引为空、读取失败或资产已丢失时，保留当前首字渐变占位，不显示破图图标。
- 浏览器模式不尝试磁盘读取，继续显示占位和现有“图片未落盘”语义。
- 每次批量加载最多同时执行 4 个 `readAsset`；20 个项目不能同时发出 20 个读取请求。
- 同一 `projectId + assetId` 在内存中复用缓存；列表刷新或搜索不重读已缓存图片。
- 缩略图只保存在 React 内存和 loader 内存缓存中，不写入 `project.json`、localStorage 或撤销/重做历史。

### 6.2 推荐模块与职责

新增 `src/services/projectThumbnailLoader.js`，保持服务层可独立用 Node 测试，不在组件里写并发队列。

建议契约：

```text
createProjectThumbnailLoader({
  readAsset,          // 注入 (projectId, assetId, maxWidth) => Promise
  concurrency = 4,
  maxCacheEntries = 100
})
```

加载器职责：

1. 接收项目摘要列表，只处理合法且非空的 `projectId/thumbnailAssetId`。
2. 用 `${projectId}:${assetId}` 作为缓存键；资产更换后键自然变化，不读取旧图。
3. 对进行中的同键请求去重，避免列表 effect 重入造成重复 IPC。
4. 用 worker/队列方式限制全局并发为 4；单个失败只把该项目解析为 `null`，不拒绝整个批次。
5. 成功结果校验 `status === 'ok'` 且 `asset.dataUrl` 为非空字符串后才进入缓存。
6. 缓存只存成功结果，失败不永久缓存，以便用户刷新列表后重试。
7. 缓存设置上限 100 并采用简单 LRU 淘汰，避免长期使用后 dataUrl 无限增长。
8. 提供 `load(projects)` 或等价批量接口，返回 `{ [projectId]: dataUrl | null }`；提供 `clear()` 供卸载或测试清理。
9. 不直接访问 `window.smartStore`，由 App 注入 `projectService.readAsset`，保持双 adapter 边界。

### 6.3 App 与组件接线

在 `src/App.jsx`：

- 用 ref 保持 loader 实例，用 state 保存 `thumbnails` 映射；不要新增持久化 reducer 切片。
- 在项目列表首次加载、手动刷新、新建/删除后列表更新时触发批量加载。
- effect 使用 `alive` 或等价取消标记，列表已变化或组件已卸载时不得把旧批次结果覆盖到新列表。
- 合并结果时以最新项目列表为准，清理已删除项目的展示映射。
- 桌面模式调用 loader；浏览器模式直接设置空映射。
- 将 `thumbnails={thumbnails}` 传给 `ProjectWorkbench`，接通已有 props。

### 6.5 F2 必测用例

1. 10 个不同资产同时加载，峰值并发 `<= 4`，最终 10 项都有结果。
2. 相同项目摘要连续加载两次，第二次命中缓存，`readAsset` 不增加调用。
3. 同一键在请求未完成时被重复加载，只产生一次底层请求。
4. 无 `thumbnailAssetId` 的项目不发起请求并回退 `null`。
5. 一个请求 reject、一个返回非 ok、一个返回空 dataUrl 时，其余项目仍成功，失败项为 `null`。
6. 同一 assetId 用于不同 projectId 时不能错误共享缓存。
7. 项目更换 assetId 后读取新图，不显示旧图。
8. 超过 `maxCacheEntries` 后按 LRU 淘汰；再次读取被淘汰项会重新请求。
9. `clear()` 后缓存清空，进行中的旧结果不会重新污染已清理状态。
10. App 手工走查：真实图片显示；删除图片文件后刷新回退首字；搜索和刷新不造成明显重复闪烁；浏览器模式无磁盘读取。
