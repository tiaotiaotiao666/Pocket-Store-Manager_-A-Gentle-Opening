## 1. 项目要解决什么

“智能开店 / 口袋店长·轻启”包含一个 Windows 桌面生成器和其生成的微信原生门店小程序。近期业务目标是完成餐饮扫码点餐答辩 MVP，后续目标是通过可验证的模板资产库，让 Agent 按店主需求组合不同小程序模板。

当前首要交付不是模板数量，而是：

```text
运维预置门店与店主
→ 顾客扫码浏览菜单
→ 创建订单
→ 演示模拟付款
→ 店主接单、制作、可取餐、完成
```

真实微信支付、退款、外送、公开店主注册、客户端授权和自动审核发布不在 MVP 范围。

## 5. 关键架构边界

### 桌面端

`App.jsx` 是组合根；组件不直接请求 API、不读取全局业务状态。服务层处理外部能力，reducer 和 domain 保持纯函数。桌面 React 小程序预览只是实时效果预览，不能替代微信运行时验收。

### 小程序

坚持微信原生，不使用 Taro/uni-app。页面组合组件并调用服务层；组件只接收 properties、只发事件，禁止 API、`globalData` 业务状态和固定路由。详见 `docs/component-contract.md`。

### 后端

NestJS 模块化，MySQL 负责业务事实，Redis 负责缓存和按需加速。API 使用 `/api/v1`，金额只用整数分并由服务端计算，门店资源按 `storeId` 隔离，角色只从数据库 membership 获取。

### Agent 与模板

`agent-turn.v1` 只负责资料收集；`agent-turn.v2` 增加受限图片与视觉抽取。2026-11-03 起 Agent 还可输出**白名单展示补丁**（主题色 / 尺寸档位 / 区块落位 / 文案菜品），但仍不能生成任意业务源码、不能增减组件，也不能绕过主题与布局约束；确定性 Composer 从可信版本化资产生成工程，并用 Lock 保证可复现。

2026-11-12 新增服务端多轮 Runtime（`agent-run.v1`）：模型通过 `get_store_draft` / `update_store_draft` 两个工具读写单次请求内的草稿，Runtime 负责 schema 校验、超时、重试、并发、结果截断、循环检测与上限；`missingFields` / `errors` / `nextQuestion` 仍由服务端重算，端点尚未接入桌面 UI。详见 `docs/agent-runtime.md`。

2026-11-17 新增 `frontend-reconstruct.v1`（图片驱动前端重构）：用户上传**恰好一张**参考截图（可附文字），服务端用视觉模型产出 `UiRequirement/VisualSpec` 与只读能力覆盖报告；模型只能通过四个受控工具（`get_frontend_capabilities` / `check_frontend_coverage` / `propose_frontend_draft` / `repair_frontend_draft`）提出需求与 `frontend-pack-draft.v1` JSON DSL，不能写任意 WXML/WXSS/JS/WXS。桌面主进程在应用私有 `<userData>/projects/<projectId>/frontend-runs/<runId>/attempts/attempt-<n>/` 物化候选与 Registry overlay，跑 Composer dry-run + `mini:check` + 一致性 + 可观察项，再按需包装真实微信验证；候选不写正式 `templates/**`、不重冻结全局 Registry，采用/撤销/重开/正式导出由项目快照与同一 overlay 保证同源。契约见 `docs/frontend-reconstruct-contract.md`，本地执行侧见 `desktop/frontend-reconstruct/README.md`。

## 7. 当前主要风险

- **本机 MySQL/Redis 未在本次任务中确认**：`docs/handoff/当前工作区交接.md` §4 记录过 2026-11-09 拉起并复跑；若 `3306`/`6379` 未监听，`server:dev` 会在 Prisma `onModuleInit` 以 `P1001` 退出，服务端 DB 集成测试与真实 Agent HTTP 调用只能标 `BLOCKED`。
- 桌面预览与导出虽已共享 CompositionPlan，但 React 仍是**复刻层**，不得当作微信真机一致；真机一致性需按人工走查清单核对。
- 图片驱动前端重构的 **P7 全量门禁与真实微信运行时验收尚未执行**：dry-run/静态门禁通过、微信工具不可用时只能是 `partial`，不得宣称“已验收”；候选采用后的导出必须使用同一私有 overlay，缺 overlay 不得回落 Base。
- `npm run agent:smoke` 在受限 agent 子会话内可能因 `spawnSync EPERM` 无法启动 Electron（`BLOCKED`）；桌面点击闭环需在普通终端或由 P7 重新执行，不能把“没跑”写成通过。
- `ChatStream` 的前端过程卡是可选 `process` prop（由 `buildFrontendProcessView` 产出）；`src/App.jsx` 接线不在 P6 文档任务范围内，P4 候选面板当前展示自身进度/候选摘要。最终展示位置需在 P7 走查确认，避免两处重复过程卡。
- 候选只存在应用私有 `<userData>` workspace；项目快照只保存相对引用/摘要/证据，删除或篡改候选必须提示并回退，不得用 Base 冒充候选。
- `composer:verify` 的 `PATH_ESCAPE` 为既有缺陷：报告文件内含绝对路径；移出两个报告文件后 8 项全绿。
- 生图通道关闭（`IMAGE_PROVIDER_NAME=not-configured`），导出仍使用 `local-demo` 占位图；本轮只交付提示词约束。
- `presentation` 展示补丁未持久化到 `projectSnapshot`，重开项目后丢失。
- `assets.images` 无删除动作，移除环境照后已写入条目不会回滚。
- Agent 的 Authorization 只检查 Bearer 形式，不是真实店主身份认证；B1 的 `SessionAuthGuard` 尚未接入 Agent。
- B1 的真实微信 `jscode2session` 未用真实凭据验证，且尚无接口限流。
- 微信开发者工具 `proxyType=SYSTEM` 会让 `cli auto` 卡 AppID 校验，需切直连；真机 HTTPS、安全区与性能仍未验证。
- 新导出工程的 `md` 档与改前视觉有差异（海报 300→240rpx、商品图 168→140rpx、store-header 增加 `min-height:190rpx`），需视觉确认。
- M7 的 `direct 2` 只代表「可进店主可选列表」，真机扫码、安全区与海报视觉未验收；不得宣称可直接上架。
