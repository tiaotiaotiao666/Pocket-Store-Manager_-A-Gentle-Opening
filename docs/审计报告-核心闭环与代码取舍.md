## 0. 一句话结论

**项目不缺"生成器零件"，缺的是"一个以版本和预览为中心的 Project Agent"。**

你要的核心闭环是：

```text
上传图片 + 语言描述
→ 项目 Agent 在当前项目版本上改代码
→ 一键唤起微信开发者工具
→ 同页面、同尺寸的「改动前 / 改动后」对比
→ 采用或撤销
```

现状是 **四套并列链路 + 两套图片识别 + 三种撤销语义**，每套都能单独跑通一段，但没有一条从头到尾。最关键的取舍判断是：

- **受控代码生成链（FrontendPack DSL → 私有 workspace → Composer dry-run → 微信运行验证）是这个项目最值钱的资产，必须留、不能删**；
- **围绕它的"机械流程外壳"（功能勾选 → 假进度构建 → 模板匹配 → 提示词 → 生图）和"第二套图片识别链"才是历史包袱**；
- **"自动前后对比"不是从零做**：微信截图自动化已经能跑并把 PNG 落盘，只是 IPC 把图片路径丢掉了、UI 只显示文件名。这属于接线工作，不是研究性工作。

### 2.1 「前后对比」为什么不是从零做

已证实的链路是通的，断在两处：

- 微信自动化确实在逐页截图并写盘：`scripts/wechat-devtools-run.cjs:284-292`（`miniProgram.screenshot` → `shots/<route>.png`）。
- 包装层也确实把截图清单返回了，含相对路径：`desktop/frontend-reconstruct/verify-runtime.cjs:277-312`。
- **但 IPC 只保留了 `{name, bytes}`，把 `path` 丢了**：`desktop/frontend-reconstruct-ipc.cjs:951-957`。
- **UI 只画文件名和字节数，没有 `<img>`**：`src/components/screenRef/FrontendCandidatePanel.jsx:355-364`。
- preload 里也没有读取候选截图的通道：`desktop/preload.cjs:90-104`。

也就是说：**图已经在磁盘上，只是没有人把它端到屏幕上。** 这一条是整个报告里投入产出比最高的改动。

## 3. P0 阻断项（不修，"一键预览"在用户机器上必然失效）

### P0-1　安装包缺候选微信验证的运行资源

- `verify-runtime.cjs` 只允许执行仓库内固定脚本，且脚本不存在即返回 `BLOCKED`：`desktop/frontend-reconstruct/verify-runtime.cjs:26-28,88-118`。
- 但 `package.json` 的 `build.files` **没有** `scripts/wechat-devtools-run.cjs`：`package.json:70-85`（只有 `scripts/composer/**`、`scripts/validate-miniprogram.cjs`、`scripts/frontend-capabilities.cjs`）。
- 该脚本还 `require('miniprogram-automator')`：`scripts/wechat-devtools-run.cjs:197-204`，而它是 `devDependencies`（`package.json:54-62`）。**高置信推断**：electron-builder 默认排除 devDependencies，安装版必然 `MODULE_NOT_FOUND` → `BLOCKED`。
- `scripts/check-packaging.cjs:63-121` 的必检清单里没有这两项，所以打包检查会"通过"，但通过**不能证明该功能可运行**。
- 佐证：`release/builder-debug.yml:6-15` 是旧构建清单，连 `templates/catalog/**`、`templates/frontend-packs/**`、能力快照都没有 → **现有 release 目录不能作为当前配置的实测证据**，必须重新打包验证。

**修法**：把固定脚本纳入 `build.files`；为 automator 做"运行时可选依赖 + 缺失时明确降级文案"（或改为按需安装并提示），并把两者写进 `check-packaging` 的必检断言。

### P0-2　候选"验证"与普通"预览"不是同一条链

- 普通预览：`devtools-launch.cjs` 要求"必须是 Composer 产物 + 必须有真实 AppID + 必须过输出一致性"，且明确只表示"已发出调起请求，不代表编译通过"。`desktop/devtools-launch.cjs:237-302, 336-348`。
- 候选验证：直接对 dry-run 输出跑 `wechat-devtools-run.cjs`，**没有**上述 AppID/产物身份预检。`desktop/frontend-reconstruct-ipc.cjs:905-939`。
- 两处的 CLI 搜索路径清单还不一样：`desktop/devtools-launch.cjs:21-56`（含注册表外的目录扫描）vs `scripts/wechat-devtools-run.cjs:25-30`（只有 4 个候选）。→ 同一台机器上可能"预览能开、验证说工具缺失"。

**修法**：抽一个 `resolveDevtoolsCli()` 单一实现，两条链共用；预览与验证共享同一份工程身份校验。

### P0-3　总体 PASS 会掩盖交互失败

判定只看页面：`scripts/wechat-devtools-run.cjs:304-305`（`report.status = failed.length === 0 ? 'PASS' : 'FAIL'`），`interactions` 里的 FAIL/BLOCKED 不参与定级；包装层只统计不降级：`desktop/frontend-reconstruct/verify-runtime.cjs:513-548`。

后果：UI 可能显示"微信真实编译与关键页面验证通过"，而"结算提交下单"其实点失败了。**这直接违背项目自己定的诚实性红线。**

**修法**：`status` 必须由 `pages` 与 `interactions` 共同决定；关键动作（下单链）失败即 `FAIL`，工具阻塞即 `BLOCKED`。

## 6. 目标架构（建议）

```text
┌──────────────────────────────────────────────────────────┐
│ 左侧：项目列表/会话        中间：项目工作区        右侧：双视图 │
│                                                    ┌────┴────┐
│                                                    │ 项目信息 │
│                                                    │ Agent对话│  ← 二选一切换
│                                                    └─────────┘
└──────────────────────────────────────────────────────────┘
中间工作区（唯一主线）：
  版本时间线  Base ─ v1 ─ v2(当前) ─ v3(未采用)
              └─ 每个版本：参考图 + 描述 + 候选引用 + 验证状态 + 截图对
底部常驻输入区：
  [📎 图片] [一句话描述………………] [发送]
  [使用微信开发者工具预览]  ← 四态：未安装/未构建/启动中/已打开/失败
对比视图：
  ┌──────────┬──────────┐
  │ 改动前    │ 改动后    │   ← 同为 pages/home，同尺寸
  │ 微信截图  │ 微信截图  │
  └──────────┴──────────┘
  + 字段级 diff（主题色/尺寸/区块顺序/文案/组件）
```

**三条硬规则**

1. **一个修改入口**：图文只有一个提交点，由 Agent 判定"这是改资料、改布局还是换骨架"，UI 不再按相位分派动作。
2. **版本不可变**：每次修改产出新候选，旧版本保留；采用/撤销只移动"当前指针"，不原地覆盖。
3. **证据同源**：对比用的两张图必须来自同一条微信运行链、同一路由、同一视口；拿不到就显示 `NOT_RUN`，不用 React 截图替代。

## 7. 分阶段落地路线

### 阶段 0：让它"真的能跑"（1–2 天，无新功能）

| 任务 | 验收 |
| --- | --- |
| 固定微信脚本 + automator 纳入打包，`check-packaging` 加断言 | 安装版点"验证"返回 `PASS`/`FAIL`/`BLOCKED` 之一，而不是必 `BLOCKED` |
| 统一 CLI 解析为单一实现 | 预览与验证在同一机器上结论一致 |
| `status` 纳入 interactions | 构造一次下单点击失败，必须得到 `FAIL` 而非 `PASS` |
| 重新打包并实测（旧 release 不可信） | 有安装包实测记录，不用源码检查代替 |

**这一阶段不做 UI 改动。** 先保证闭环的"手"能动。

### 阶段 1：把画面端到屏幕（3–5 天，投入产出比最高）

**关键约束**：截图只从私有 attempt 目录读，不新增任意读盘通道；不得用 React 预览截图冒充。

## 8. 不要做的事

1. **不要为了"前后对比"去接生图模型或做像素相似度打分**。对比的语义是"同一页面改前改后"，不是"像不像参考图"。
2. **不要删受控 DSL / renderer / overlay / dry-run / verify-runtime**。它们是唯一能让"AI 改代码"可交付的东西。
3. **不要用 React 预览截图当微信运行时截图**，也不要在拿不到截图时把 `partial` 写成通过。
4. **不要为了让门禁变绿而放宽测试**；基线失败要单独修、单独留证。
5. **不要在过渡期直接物理删除 `screen-reference` 相关代码**，先断入口、保留旧快照读取，否则旧项目打不开。
6. **不要把 `miniprogram/` 当交付物或预览目标**，它是只读镜像。

## 9. 需要你决策的 5 个问题

1. **门店资料还要不要"先填再选功能"？** 我的建议：进项目第一屏就是"描述 + 传图"，资料由 Agent 边聊边补，取消单独的"资料表单阶段"。
2. **功能勾选保留到什么程度？** 我的建议：只作为"告诉 Agent 你要什么"的输入，不再驱动构建，也不再出现"加入定制能力"这种会误导的按钮文案。
3. **生图与海报是保留、延后还是删除？** 我的建议：移出主流程，代码移到 demo 或删掉，只留 provider 接口。
4. **对比视图的基线取哪个？** 建议默认"上一个已采用版本"，并允许切到"Base"。这决定版本模型怎么建模。
5. **Agent 对话是"每项目一个长会话"还是"每版本一个会话"？** 建议每项目一个长会话 + 按版本打标记，避免会话爆炸。
