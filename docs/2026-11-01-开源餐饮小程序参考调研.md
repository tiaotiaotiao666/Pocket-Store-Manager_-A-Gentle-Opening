# 2026-11-01 开源餐饮小程序参考调研

> 面向后续 AI 与开发者：本文记录"在 GitHub 上找原生微信小程序餐饮模板、拉取并对照本项目模板"的完整结论。
> 结论先行：**没有可直接替换或直搬的开源项目**；可借鉴的是交互与信息架构，不是分层与状态管理。

## 1. 本轮目的与范围

- 目的：为 `miniprogram/` 与 `templates/base/ordering-base` 寻找可参考的餐饮点餐实现，判断哪些能提升本项目模板的完成度。
- 范围：检索 → 技术栈核实 → 许可证核实 → 拉取 → 结构对比 → 可借鉴/不可借鉴清单。
- 不在范围：未修改任何业务代码；未替换模板；未新增依赖。

## 2. 本项目模板的"要求"基线（用于判断"一样"）

取自 `miniprogram/app.json` 与 `templates/base/ordering-base/1.0.0/manifest.json`：

| 维度 | 本项目基线 |
| --- | --- |
| 框架 | 微信原生小程序（WXML/WXSS/JS），不用 Taro / uni-app |
| 页面 | 7 个：home、menu、checkout、orders、order-detail、mine、merchant-orders |
| 组件 | 14 个，只通过属性收数据、通过事件抛意图，组件内不调 API、不依赖 globalData 与固定路由 |

**判断结论：GitHub 上没有同时满足"原生 + 组件化 + 服务层 + 领域纯函数 + 六态订单 + 店主端同工程"的餐饮开源项目。** 最接近的只是在业务覆盖面或页面数量上接近。

### 6.1 点餐双栏布局（参考 wechatscan）

- 文件：`.tools/refs/wechatscan-master/page/diancan/index.wxml:25-60`
- 做法：左侧分类 `scroll-view` + 右侧菜品 `scroll-view scroll-into-view`，分类上显示该分类已选数量角标。
- 对应本项目：`components/category-nav` 与 `pages/menu`。本项目已有双栏，可借的是**分类角标数量**与点击分类平滑定位。

### 6.2 加购抛物线动画（参考 wechatscan）

- 文件：`.tools/refs/wechatscan-master/page/diancan/index.js:98-138`
- 做法：`wx.createAnimation` 先平移再回落，制造"菜飞入购物车"的视觉反馈。
- 对应本项目：`components/cart-bar` 可加动效，纯视觉，不触碰数据流。
- 注意：该实现混在 497 行页面逻辑里，**只取动画片段，不要连带其 globalData 写法**。

### 6.3 规格/口味选择模型（参考 coco）

- 文件：`.tools/refs/imitate-coco-xcx-master/pages/list/list.js:19-21`

## 11. 补查：顾客端与店主端是合并还是分开（2026-11-01）

### 11.1 四种参考对象的真实做法

| 对象 | 形态 | 证据 |
| --- | --- | --- |
| `mhzqx-weChatApp` | **合并**：同一小程序内同时有顾客页与店主页 | `app.json` 的 `pages` 同时列出 `pages/menu`、`pages/order` 与 `pages/severmenu`、`pages/severalertfood`、`pages/severaddfood`、`pages/severadmin`、`pages/severinfo`；无 tabBar，靠页面跳转进入 |
| `bee` | **顾客小程序 + 第三方 Web 后台**，小程序内保留轻操作 | 36 个页面全是顾客侧；README 第 72–97 行要求注册「api工厂后台」；第 137–147 行说明商家在「我的 → 扫码核销」核销，且用 `order_hx_uids` 白名单控制入口显隐 |
| `wechatscan` | **顾客小程序 + 独立后台** | README 第 33–53 行单列「后台功能」：门店、菜品、桌台、台牌打印、打印机、前台订单、厨房订单、营业日报 |
| `imitate-coco-xcx` | **纯顾客端演示** | 7 个页面，无任何商家页，接口用已失效的 easy-mock |

### 11.2 结论：行业没有统一答案，按规模分层

| 场景 | 主流形态 | 原因 |
| --- | --- | --- |
| 单店 / 自研 / 答辩 MVP | **合并**：一个小程序，按角色分流 | 一个 AppID、一次审核、一套代码、订阅消息统一、演示成本最低 |
| 单店但有 3 人以上店员、要小票打印/报表 | **顾客小程序 + PC/H5 后台** | 重操作（批量、打印、日报）在后台更高效，小程序只留核销等轻操作（bee 就是这种） |
| 连锁 / 多门店 / SaaS 服务商 | **双端分离**：顾客小程序 + 独立商家端（小程序/App/PC） | 体验隔离、权限安全、审核风险隔离、团队可并行发布 |

关键判断不是"合并还是分开"，而是**哪些操作算重操作**：改菜品、看报表、打印、批量处理 → 后台；核销、接单、改状态 → 可留在小程序。

### 11.3 微信平台侧的硬约束（决定拆分成本）

- 一个小程序对应一个 AppID；双端分离意味着两个 AppID、两次认证、两次类目审核、两次发布与版本回滚。
- 商家端涉及餐饮经营功能，类目与资质要求比纯顾客端更高；多商家"点餐平台"类目通常还需额外经营资质。
- 订阅消息模板按 AppID 配置，"新订单提醒"发给店主需要店主自己订阅，与顾客的"出餐提醒"是两套模板。
- 同一包内含商家管理页时，审核员可能要求提供可登录的商家演示账号；无法演示会被判"功能不完整"。
- 包体积：商家页会被打进同一个包；后续商家功能变重时，应把商家端拆成**分包**按需加载（主包/分包体积上限以微信当期规则为准）。

### 11.4 本项目现状：属于"合并 + 后端角色门禁"

| 事实 | 位置 |
| --- | --- |
| 店主入口不在 tabBar，而在「我的」页内按角色显隐 | `miniprogram/pages/mine/index.js:62-66` |
| 点击后跳转商家工作台并带 `storeId` | `miniprogram/pages/mine/index.js:120` |
| 角色判定基于服务端返回的 memberships（OWNER/STAFF） | `miniprogram/services/session.js:140` |
| 商家工作台分「待处理 / 进行中」并轮询 | `miniprogram/pages/merchant-orders/index.js:12-17` |

即：与 `mhzqx` 同属合并式，但角色门禁放在服务端，比 `mhzqx` 的"页面随便跳"更严格。

### 11.5 对本项目的建议

1. **答辩 MVP 保持合并**：单 AppID、演示链路已通（加购→结算→支付→接单→制作→可取→完成），拆分只会增加演示成本。
2. **守住三条边界**：商家入口不进 tabBar（已满足）；前端只做显隐、后端必须强制鉴权（已满足）；商家页不得复用顾客页的"模拟支付"入口。
3. **产品化再拆**：拆分时 `services/` 与 `domain/` 可原样复用，只拆 `pages/` 与 AppID，后端 `/api/v1` 不变；若暂不拆，先把商家页挪进分包。
4. **何时必须拆**：出现多门店切换、多员工权限分级、小票打印、营业日报、审核被要求商家演示账号且无法提供时。
